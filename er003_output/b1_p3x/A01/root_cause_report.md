# ER-003-B1-P3X 根本原因レポート

## 結論

**根本原因はコードのバグではなく、Gemini TTS(`gemini-2.5-pro-preview-tts`)が、
マーカー語入りの日本語原稿に対して、日本語ではなく英語の音声を生成したことである。**
これは切り出し・結合・Dynamics3のいずれの処理より前、TTS API呼び出しの応答そのものの
時点で既に発生していた(Step 2の分岐A「`ja_with_spoken_marker.wav`が英語」に該当)。
このため、指示section「Step 2｜A」の明記通り、切り出し・結合(Step 5)へは進まず、
ここで停止して報告する。**新規TTS callは行っていない。**

## 確認した事実

1. `raw/ja_with_spoken_marker.wav`(現在のファイル、sha256 `56349635...`)を
   Azure STTで診断したところ、日本語ではなく流暢な英文として認識された
   ("the first half is marked by intense physical contact and a sense of tension
   with both teams unable to register a shot on goal leading to a quiet stalemate")。
2. P3W実行時に意図せず発生した1回目のTTS生成結果(sha256 `f3856d42...`、診断用に
   複製した`mfa_tool/fresh_marker_corpus/test_fresh.wav`として現存)も、独立して
   別の言い回しの英文として認識された。**1回目・2回目とも、それぞれ独立して
   英語化していた**(同一バッファの使い回しではないことを、2回の生成結果の
   文言が異なることから確認)。
3. 対照として、同じスタイル指示(`build_style_prefix()`、無変更)と、ほぼ同一の
   日本語原稿(マーカー語を含まない版)を使ったP3Tの`ja_full_sentence.wav`は、
   Azure STTで正しく日本語として認識された。診断ツール自体の誤設定ではないことを確認。
4. Pythonから実際にTTS APIへ送信したプロンプト本文(`build_tts_prompt`の出力)を
   再構築して確認したところ、**送信したテキストは正しい日本語のマーカー入り原稿
   そのものであった**(「前半は激しい接触と緊張が続き、両チームとも枠内シュート、
   キーワード挿入位置を記録できないまま、静かな均衡が保たれます。」)。
   つまり、リクエスト側に文字化け・取り違え・英語混入は一切ない。

## 根本原因の特定

送信したプロンプト(リクエスト)は正しい日本語だったにも関わらず、TTS APIからの
レスポンス(応答音声)が英語だった。これはPythonコード側の問題ではなく、
Gemini TTSモデル自体が、この特定の入力に対して英語音声を生成したことを意味する。

推定される誘因(確定はできないが、状況証拠から最も妥当な仮説):

- 採用済みのスタイル指示(`er002_common.build_style_prefix()`)の1行目は
  "TTS the following complete story in **natural, engaging English**." であり、
  英語での読み上げを前提とした文言になっている(このプロジェクトの本来の用途である
  英語記事の読み上げ向けに設計された指示であり、これまでP3R〜P3Wの日本語音声生成では
  問題なく機能していた)。
- 今回追加した一時的なマーカー語「キーワード挿入位置」は、カタカナ語「キーワード」
  (英語"keyword"のカタカナ表記)を含み、かつ意味的に「(ここに)キーワードを挿入する
  位置」という、TTSへの編集指示のように読めるメタ的な文言である。
- この「英語での読み上げ」を前提とする指示と、「キーワードを挿入する位置」という
  メタ的に読めるカタカナ語主体の一時原稿が組み合わさったことで、モデルが原稿全体を
  文字通り読み上げず、英語へ意訳・翻訳して読み上げる挙動を引き起こした可能性が高い。
  1回目・2回目で言い回しが異なる(が意味内容は同じ)ことも、逐語的読み上げではなく
  意訳的生成が起きていたことと整合する。

この仮説は状況証拠に基づく推定であり、Gemini TTSモデル内部の挙動を直接検証すること
はできない。ただし、**Pythonコード側(TTSリクエストの構築・保存・切り出し・結合)には
問題がないこと**は、上記4点の事実確認によって明確に切り分けられている。

## 対象外だった原因候補(確認の結果、否定されたもの)

| 候補 | 確認結果 |
|---|---|
| 英語response/bufferの使い回し | 否定。1回目・2回目の生成結果は文言が異なり、それぞれ独立して生成されたことを確認 |
| キャッシュ | 否定。本パイプラインにTTS結果をキャッシュする仕組みは存在しない(`er002_gemini_client.make_tts_call_fn`は毎回`generate_content`を呼び出す) |
| 切り出し元pathの取り違え | 否定。`ja_before_marker.wav`/`ja_after_marker.wav`は、正しく`raw/ja_with_spoken_marker.wav`から、正しいframe範囲([0,5.79)秒・[6.71,末尾)秒、P3Wで取得済みのmarker start/endと一致)で切り出されている。切り出し処理自体に誤りはない |
| component間・concat時の変数衝突 | 否定。`en_shot_on_target_trimmed.wav`のsha256はP3Uの正規成果物と完全一致しており、英語コンポーネントの内容自体は正しい。3コンポーネントの連結順・境界無音長も指示通り |
| Dynamics3による内容変化 | 否定。Dynamics3は音量調整処理であり音声内容(言語)を変更しない。raw時点で既に英語だったことがfinalへそのまま引き継がれているだけ |
| 同名ファイル上書き(プロセス上の問題として実在) | **これ自体は実在した**(P3W完了報告で開示済み: デバッグ中に既存ファイルを確認せずスクリプトを再実行し、2回目のTTS呼び出しが発生・1回目を上書き)。ただし、1回目・2回目のいずれの生成結果も独立して英語だったため、この上書き自体は「英語化」という結果の原因ではない(上書きがなくても1回目の時点で既に英語だった) |

## 今回とらなかった対応

指示section「禁止」に従い、以下は一切行っていない。

- 原稿変更
- 新TTS instruction
- 別voice
- 再TTS生成
- ASRで境界を再推定
- MFA時刻の手動補正
- 最長無音方式
- 大規模リファクタリング

## 結論・停止理由

正常な日本語のマーカー入り音声は、1回目・2回目のいずれの生成結果にも存在しない
(指示section「停止条件」の「raw日本語自体が英語で、正常な日本語sourceが存在しない」
に該当)。既存音声だけでの再構築(Step 5)を行うための有効な日本語sourceがないため、
ここで停止する。新しいTTS生成でこの原稿を再度読み上げさせることは、指示Step 2Aの
「新規TTS callは禁止」に反するため行っていない。

音声品質・再生成方針の最終判断はユーザーが行う。
