# ER-003-B1-P5B Google Cloud TTS／Amazon Polly比較検証

## 1. 目的
ER-003-B1-P5Aで未実施だった以下の2エンジンについて、P4Dと同一の全文ひらがな入力を使用し、原稿忠実性と日本語の自然さを確認する。

1. Google Cloud Text-to-Speech
2. Amazon Polly Neural

Azure Speech `ja-JP-NanamiNeural` は、ユーザー試聴により以下の理由で不合格となった。

* 全体が自然な日本語読み上げになっていない
* 「何が起きる」を「なんがおきる」と発音した

Azureの追加調整・再生成は行わない。

## 2. 今回確認する仮説
以下の2つを切り分ける。
仮説A
Azure Speech固有の問題であり、Google Cloud TTSまたはAmazon Pollyでは、同じ全文ひらがな入力でも自然に発話できる。
仮説B
全文ひらがな入力そのものが、単語境界、意味、アクセントまたは読みの解釈を不安定にしている。
今回の2エンジンでも不自然な読みが発生した場合、エンジン選定だけでなく、全文ひらがな正規化方式を見直す。

## 3. 比較対象
Google Cloud Text-to-Speech

* Language code：`ja-JP`
* Voice：`ja-JP-Neural2-B`
* 入力形式：plain text
* SSML：使用しない
* 話速指定：使用しない
* pitch指定：使用しない
* volume gain指定：使用しない

Amazon Polly

* Language code：`ja-JP`
* Voice：`Kazuha`
* Engine：`neural`
* Text type：plain text
* SSML：使用しない
* Lexicon：使用しない

勝手に別のvoiceへ変更しない。
指定voiceまたはengineが利用できない場合は、エラー内容と利用可能なvoice一覧を報告し、代替voiceで生成せず指示を待つ。

## 4. 入力
以下のP4D保存済みファイルを変更せず使用する。
`pattern_a_full_hiragana.txt`
P5Aで使用した入力と同じsha256になることを確認する。
期待される既存ハッシュ：
`fb9ea8c9...`
省略値だけでは厳密比較できないため、実行時には完全なsha256を保存・報告する。
以下を変更しない。

* 文字
* 読み
* 句読点
* ダッシュ
* 空白
* 「めじるし」
* 文の区切り
* 語順

エンジンごとの読み改善を目的とした入力変更は禁止する。

## 5. 認証・環境確認
実装または音声生成の前に、各環境について以下を確認する。
Google Cloud

* 必要なPythonクライアントライブラリ
* Cloud Text-to-Speech APIの利用可否
* Application Default Credentialsまたは既存の安全な認証設定
* 利用プロジェクト
* 課金設定またはAPI呼び出し可否

AWS

* boto3または既存のAWS SDK
* 既存のAWS認証情報
* 利用プロファイル
* 利用リージョン
* `polly:SynthesizeSpeech` の実行可否

秘密情報の値は、ログ、レポート、テスト出力、Git管理ファイルに記録しない。
以下を禁止する。

* APIキーやsecret keyのソースコードへの直書き
* 認証情報を `.env.example` に実値で記載
* 認証ファイルのコミット
* ユーザーの許可なしに新しい恒久的アクセスキーを作成
* 認証情報を実行報告へ出力

認証が利用できない場合は、実装を勝手に別サービスへ切り替えず、ユーザーが行う必要のある設定を具体的に報告する。
認証可能なエンジンだけ先行生成してよい。

## 6. 生成条件
各エンジンにつき、全文を1回のTTS API呼び出しで生成する。
technical retryは、通信エラー等の明確な失敗時だけ許容する。その場合は実呼び出し回数と理由を記録する。
以下は実施しない。

* chunk分割
* 文単位の分割生成
* marker変更
* 英語音声への置換
* MFA
* Dynamics 3
* 音声速度変更
* pitch変更
* SSML
* 発音辞書
* 語句別の例外
* 原稿の修正
* Azureでの再生成
* Gemini TTSでの再生成

ファイル形式を揃えるためのコンテナ変換が必要な場合は、音声内容、速度、ピッチ、音量を変化させない。

## 8. 機械QA
各エンジンについて以下を確認する。

* P4D/P5Aと同じ入力ハッシュである
* API送信文字列が保存済み入力と一致する
* TTS API callが1回である
* chunk分割を行っていない
* 音声ファイルが正常にdecodeできる
* clippingなどの重大なファイル異常がない
* 5回の「めじるし」がASR上存在するか
* 次の対象句がASR上どのように認識されたか

対象句：

1. せんしゅをこうたいでさげる
2. めじるしというけつだんで
3. しゅびをかため
4. わずかなりーど
5. さいごのすうふん
6. なにがおきる

特に「なにがおきる」が以下のどちらとして認識・発話されるかを記録する。

* なにがおきる
* なんがおきる

ASR結果は診断情報として使用し、単独で合否を決定しない。
類似度スコアが高くても、部分的な語句欠落や不自然な読みを合格扱いにしない。

## 9. ユーザー試聴項目
各音声について、ユーザーが以下を確認する。
原稿忠実性

1. 「選手を交代で下げる」が省略されていない
2. 「目印という決断で」が省略されていない
3. 「守備を固め」に「る」が追加されていない
4. 5つの「目印」がすべて発話されている
5. その他の語句に欠落・追加・言い換えがない

読み

6. 「最後の数分」が正しい
7. 「何が起きる」が「なにがおきる」と発話される
8. 「わずかなリード」の読みとアクセントが自然である

音質・自然さ

9. 日本語として自然なイントネーションである
10. 全文が不自然に平坦でない
11. 語句の区切りが自然である
12. 声色が大きく変化しない
13. Listening Previewとして最低限許容できる

音声の自然さに関する最終判断はユーザー評価を優先する。

## 10. 合格条件
エンジンごとに以下をすべて満たした場合のみ、P5B合格候補とする。

* ユーザー試聴で原稿内語句の欠落がない
* 原稿外の語句追加がない
* 意味を変える言い換えがない
* 「なにがおきる」が正しく発話される
* 重点語句の読みが正しい
* 日本語イントネーションがPreview用途として許容できる
* 声色の連続性に重大な問題がない

原稿忠実性を満たしても、日本語が全体として不自然なら不合格とする。

## 11. P5B後の分岐
少なくとも1エンジンが合格
合格したエンジンを対象に、同一入力で複数回生成し、原稿忠実性と音声品質の再現性を検証する。
原稿忠実性は合格だが、両方とも日本語が不自然
全文ひらがな正規化方式が自然さを損ねている可能性が高い。
次工程では、最も原稿忠実性が高かったエンジンを使い、以下の入力方式を比較する。

* 元の漢字かな交じり原稿
* 必要箇所だけ読みを制御した原稿
* 全文ひらがな原稿

この比較は別管理IDで行う。
いずれも原稿を省略・変更
現在のPreview構成をTTSで安定生成できない可能性を再評価する。
語句単位の場当たり的な修正には戻らず、原稿構造または生成方式の変更を検討する。
