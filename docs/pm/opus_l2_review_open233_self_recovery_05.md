# Opus独立レビュー: OPEN-233 違反範囲の受け渡し再設計(design_open233_violation_span_handoff_01.md)

## 1. 総合結論
- **変更は必要。** 現行の「Checkerの文字列を手がかりに、記事から対象を推測し直す4段構え(+JA側の5段)」が、2回続いた個別修正(委任_35/36)の共通原因になっている。ここを「確認済みの範囲をそのまま使う」形に置き換えるのが正しい方向。
- **推奨は「一部修正」。** 段階0(Checker Promptを変えず、`claim_in_article`から範囲を機械的に復元する)を本体にする。段階2の`violation_spans`(新しい出力欄)の追加と、案J1(JA対応文をCheckerに返させる)は保留にする。
- 段階0の正規化には次の3つを足す: (a) 引用断片の分解(N5)は、断片以外の部分がつなぎ語だけの場合に限る、(b) 一致した断片をその文全体まで広げる(文単位スナップ)、(c) 書き換えは1指摘につき1回の呼び出しで全範囲を渡し、段落を読み取り専用の文脈として付ける。
- **ただし受け渡しを直しても人間確認(Stage 4)はゼロにならない。** 再検査が毎回新しい指摘を出す揺れ、判定役の重大度判定の揺れ、JA/EN対応の3つが別に残る。

## 2. 条件B(2回修正して再発)の判定: 根本設計の問題
- 現行は、Checkerの出力を「確定した範囲」ではなく「探すための手がかり」として扱い、問題が出るたびに推測の段を足してきた(hint引用→包含スパン→類似度→単語重なり、JA側は位置比まで)。委任_36の包含スパンもこの延長にある。段を足すたびに「縮める/広げる」の別の変種が生まれる構造なので、個別バグの連続ではない。
- ただし、meta_run03_standardのStage 4は受け渡しだけが原因ではない(7節)。根本原因は少なくとも3層ある。受け渡しはそのうち最も決定論的に直せる1層。

## 3. ユーザー指定12項目への個別回答
1. **後段で探し直す必要はあるか → 不要。** 必要なのは「記事に本当にあるかの確認(完全一致)」と「書き戻す位置の確定」だけ。類似度で選ぶ処理は不要。rep21 s1の取りこぼしは、両端の“ ”を外すだけで解決する(`locate_best_sentence`は引用符付きのまま完全一致を試している runner:2249)。しかも引用符を外す関数`_strip_wrapping_quotes`はStage 2側に既にある(stage2:195)。後段の部品間で処理が揃っていないこと自体が原因。
2. **範囲をそのまま渡せば十分か → ほぼ十分。** 条件は2つ。(i) 文の一部だけの断片は、その文全体まで広げる(Checkerが指した文の中に留まり、他の文は足さない)。(ii) 書き換え役に段落を読み取り専用で見せる。現行のE1/E2 Promptは対象文しか渡しておらず(runner:2557-2599)、「They did not realize it.」のように単独では意味が取れない文を直させている。
3. **複数文・離れた複数箇所を安全に扱えるか → 扱えるが「1範囲=1回の書き換え呼び出し」は非推奨。** rep20 s2の2文は同じ段落の一続きの話で、別々に直すと文同士の整合が崩れうる。**1指摘=1回の呼び出し**で全範囲を渡し、範囲ごとの書き換え結果をJSON配列で返させる方がよい(呼び出しも減る)。配列の個数や順序が合わなければ失敗扱い(人間確認側)。
4. **文ID・文字オフセットは必要か → 不要(過剰設計)。** 設計案の比較(§6)に同意する。JA/ENの文数が合わない、書き換え後に位置がずれる、という理由で不利。
5. **位置情報は「記事へ戻す工程」だけに使えるか → できる。** 書き戻す直前に完全一致で1箇所を確認して`.replace(…,1)`するだけで足りる(現行2832の延長)。オフセットを持ち回る必要はない。
6. **JA/EN同時修正に問題は出ないか → 出る。この設計で最も弱い部分。** 詳細は5節の修正案6。
   - 段階0だけではJA対応範囲を出す手段がない。設計どおりだと`ja_source`起源の指摘はすべて「EN側だけ直す」経路に落ち、JA再検査で次の周回に回る。
   - 「JA再検査の指摘の文字列はJA文」という逆方向のケースも、照合先をEN記事に限ると全件不一致になり、人間確認が増える。範囲の照合はEN・JA両方の本文に対して行い、どちらにあるかで振り分ける必要がある。
7. **Hook/Title/本文の区分を壊さないか → 壊さない。** 「範囲がどの区分に含まれるか」で判定する方が、現行の類似度で1文を選ぶ方式より正確。複数区分にまたがる場合は「最も保護の強い区分」を指摘全体の区分とする案で妥当。加えて、hook保持などの書き換え制約は範囲ごとに適用すること。
8. **retry/fallback/再検査と整合するか → 整合する。** 周回上限・ラダー・⑥無効・JA fail-open封鎖は変わらない。注意点は2つ。
   - 周回をまたいで同じ指摘かを判定する部分(`find_matching_prior_record`、`normalize_claim_text(claim_in_article)` runner:4255)は今も生の文字列を使う。正規化後の範囲に揃えないと、同一判定が揺れる。
   - 再検査へ渡す`prior_issues`(4500)にも正規化後の範囲を渡すこと。
9. **人間確認を本当に減らせるか → meta_run03_standardの2件の主因には効く。他記事は不明で、増える方向のリスクもある。** 最近の失敗では`ja_deviation_unresolved`も頻発している(bgroup_B3、hormuz、meta rep11)。不一致を即人間確認にすると、現行fallbackで直せていた分(全体の(d)区分=8.5%)が人間確認に回る。後者は5節の修正案3で緩和できる。
10. **新しいFailure modeを作らないか → 1つ見落としがある。** 引用断片の分解(N5)が、Checkerの説明文を断片に分解して範囲を**縮める**。実データ: rep20 s2 cycle2の`same_fact_id_locations`=`Paragraph beginning “People asking Muse to call”`。N5を無条件にかけると、Checkerが「段落全体」を指したのに冒頭の数語だけが対象になる。ユーザーが禁じた「縮小」そのもの。修正案1で防ぐ。
11. **個別パッチではなく再発防止になっているか → 推測の段を全部外して「確認できなければ止める」に変えるなら再発防止になる。** 逆に、hint引用や類似度を「保険」として一部でも残すと、元の構造に戻る。
12. **さらに単純な代替案はあるか → ある。** 5節の修正案1〜6の構成が設計案より単純(Checker Prompt・schemaの変更なし、LLM呼び出しの追加なし)。
   - 1行修正案(引用符を外すだけ)の評価: rep21 s1は直る。rep20 s2(“A” and “B”の形)は直らない。「最小で十分」ではない。

## 5. 修正提案・代替案(優先順)
1. **N5は限定して使う。** 引用断片以外の部分が、つなぎ語・句読点(and / , / ; / 、 / と など)だけのときに限って分解する。それ以外は「逐語ではない」として扱う。→ 縮小リスクがなくなる。不一致はわずかに増える。
2. **文単位スナップ。** 一致した断片を、その断片を含む文の頭から終わりまで広げる。段落はまたがない。→ 「Some calls…」(記事では「Also, some calls…」)を文の途中から書き換えることで起きる大文字・小文字の乱れや、末尾ピリオドの欠けがなくなる。Checkerが指していない文は加えないので、再解釈には当たらない。設計案自身の「文全体を引用」方針(§2-2)とも一致する。
3. **不一致の扱いを「A+限定救済」にする。** Checkerの文字列が照合できないときに限り、**Stage 2のhint引用が記事に逐語で1箇所だけ存在する**場合はそれを範囲として採用する。記録には`span_source=stage2_quote`と残す。どちらも照合できなければ人間確認(A)。
   - これは類似度ではなく「別のLLMが宣言した逐語範囲を機械的に確認する」処理で、J1と同じ性質。
   - 追加費用¥0で、人間確認の増加を抑えられる。
   - 優先順位はあくまで「Checker→hint」。現行のhint優先には戻さない。
4. **書き換えは1指摘=1回の呼び出し。** 全範囲を配列で渡し、範囲ごとの書き換え結果を配列で受け取る。段落は読み取り専用で付ける。ガードは「Checkerが指した各範囲が変化したこと」を必須条件にする(離れた範囲は個別にCheckerが指したものなので、一部だけ直った状態を通さない)。
5. **delete型の再出現確認は「削除」ではなく「置き換え」。** 類似度による確認(runner:2769)を外す代わりに、「どの範囲の文字列(正規化後)も記事に残っていないこと」の完全一致確認を残し、意味の上での判定は再検査に任せる。
   - 現行の類似度確認は、誤検出でも⑥無効→`ladder_exhausted`→Stage 4へ直行する。誤検出による人間確認を作っていた可能性がある。
   - 「何も確認しない」にはしない。安全装置の弱体化に見えないようにするため。
6. **JA側。** 次の順にし、位置比による近似(J3)は外す。
   - ① Stage 2のhintにJA逐語引用があり、`ja_full`に1箇所だけ一致すれば、それをJA対象にする。
   - ② なければEN側だけ直し、JA再検査に任せる(J2)。
   - ③ 範囲の照合はEN・JA両方の本文に対して行い、言語ごとに振り分ける(3-6の逆方向問題への対応)。
   - J1(Checkerに返させる)は②が多すぎると分かった場合の次の段階。J1も①も「LLMが宣言した対応を存在確認するだけ」で性質は同じ。①は既存データで動く。
   - JA/ENペアでの書き換えは、ガードが「JAもENも変化した」ことを要求している(runner:3063-3066)。そのため、対応の誤ったJA文を無理に書き換えさせる構造が残る点は既知の限界として扱う。
7. **`violation_spans`は保留。** 段階0で不一致率を測ってから判断する。追加する場合は、`claim_in_article`との二重化を避ける。対象決定・Stage 2への表示・`prior_issues`・同一判定のすべてを1つの欄から作ること。
