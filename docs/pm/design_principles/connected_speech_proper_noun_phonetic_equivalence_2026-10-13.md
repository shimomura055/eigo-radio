## 1. 基本原則(ユーザー合意、原文に忠実)

> 原文とASR結果の文字列差分を、**発音上の同等性**と**自然な音声変化**に基づいて評価し、**同じ音韻現象には同じ判定**を適用する。ただし、実質的な発音・内容の誤りを許容しないための**安全条件**を維持する。これはMelos専用ではなく、固有名詞・一般語を含む**全Family共通**の設計指針とする。

## 2. 必須8項目

### 2-1. 文字列一致ではなく発音上の同等性を評価する思想
- ASR(音声→文字)は、同じ音を複数の綴りで返す(例: `Mello`/`Mellow`/`Melo`、`wait`/`weight`)。**綴りの違い自体は音声の誤りを意味しない**。
- したがって判定は「文字列が一致するか」ではなく「**音素列として同等か、自然な音声変化(連結発音)で説明できるか**」を軸に置く。
- 既存の承認済み原則(連結発音の許容: 「自然な英語で、子音が連続することにより一方の音が融合・弱化・脱落し得る場合、その音韻構造を診断し、正常な連結発音で説明できるなら許容する。ただし文脈によるASRの推測だけを根拠に自動PASSしない」)の延長線上にあり、新しい思想ではない(PM_GOVERNANCE 21節 分類=A: 既存仕様あり)。

### 2-2. 現在の連結発音許容原則とその実用的な許容判断
- 現行Pattern A(`er011_b1_connected_speech_validator_01.py::classify_connected_speech` L125-、`s_suffix_label_if_match` L87)は、`Melos said`に対するASR`Melo said`を**綴り水準**(`canonical == asr + "s"/"es"` かつ次語頭が歯擦音)で許容している。
- 語末の`/s/`と次語頭の`/s/`が融合して1つの長い`/s/`になるため、**どちらの/s/が失われたかを音響的に完全証明できなくても、この連結発音構造で説明できれば実用上許容する**。これが既存の判定思想であり、本原則はこれを維持する。
- 同じ現象の一部だけに異なる厳格な証拠基準を課してはならない(下記2-3)。
- ただし、この既存許容原則自体に**誤PASSリスク**(語末sを本当に落とした音声、または`s`が元から無い別語との区別が綴りだけでは付かない)があることは認識し、必要な安全性検証を行う(OFFLINE_EVAL_01の評価B・受理面拡張プローブ参照)。現行Pattern Aが後続の食い違いを検査せず最初の食い違い語のみで判定する性質(`word_diff`の最初の差のみ)も既存の限界として記録している(`er068_..._test_01.py::test_existing_pattern_a_first_diff_only_hole_is_recorded`)。

### 2-3. 同音異綴りを同一基準で評価する理由
- 目標: `Melo said`:PASS(現行) / `Mello said`:現行UNCERTAIN。**同じ音素列として確認できるASR転写に対し、同じ連結発音判定を適用する**(綴りが違うだけで扱いが変わる非対称を作らない)。
- 理由: (a)綴りはASRの癖であり音声の品質情報ではない。(b)一部の綴りだけ緩く、別の綴りだけ厳しいと、量産時にHuman Review(HR)が綴りの偶然で増減し、再発する(Melo/Mello非対称、OPEN-327/330)。(c)全Family共通で再利用できる判定にするには、綴りの個別登録ではなく音素水準の等価性で表現する必要がある。
- `Melos`/`Melo`/`Mello`/`Mellow`/`Mellos`は**説明用の例にすぎない**。これらの綴りを個別登録するだけの対応や、Melos専用hardcodeは**禁止**する。

### 2-4. 単語単体の発音と連結発音後の発音の区別
- **単語単体の読み**: 辞書(CMU等)・確認済み発音・Ledger上のその語の音素列。
- **連結発音後の読み**: 語境界の子音連続により、語末/語頭の子音が融合・弱化・脱落・再分節した後の音素列。
- この2つを混同しない。例: `Melos`の単体音素は`M EH L OW Z`(推定)、`Melos said`の連結後は`M EH L OW S EH D`(語末Zと語頭Sが融合)であり、ASRの`Mello said`は連結後の音素列と同等。単語単体で`Mello`≠`Melos`だからといって連結後も不一致とは限らない。逆に、連結で説明できるのは**境界の子音1つ**に限る(母音が違う、別の子音が違う、は説明できない)。

### 2-5. 固有名詞だけでなく一般語にも適用する
- 同音異綴り・連結発音は一般語でも起きる(`studies suggest`→`study suggests`、`pay showed coffee`→`pay show coffee`、`wait`/`weight`)。固有名詞専用の別機構を作らない。
- 固有名詞と一般語で**証拠の質が違う点だけ**を区別する: 一般語はCMU辞書が実際の発音を概ね反映するが、固有名詞はCMU登録が偶然・不正確な場合がある(`Tse`の実例、Production`entity_word_arpabet_primary_match`は代表発音のみの保守基準)。この保守基準は固有名詞側の**確認の質**であり、許容基準を変えるものではない。

### 2-6. 実際の誤発音・内容変更を許容しない安全条件
次は**許容しない**(自動PASSにしない。既存判定へ委譲またはHR):
- 否定の反転・欠落(`can't talk`→`can talk`、`not`/`never`/`no`)
- 時制・語尾の変更(`walked`→`walk`で意味が変わる場合、過去/現在)
- 数・数量の変更(`three`→`tree`、`six`→`sick`)
- 固有名詞の別名への置換(`Melos`→`Marcus`/`Melon`/`Melody`)
- 語の欠落・誤語・余分な語(`Melos said`→`Melos`/`Melos said it`)
- 母音や他の子音が実質的に異なる転写(`Mellis`、`Mallow`は現行の判定器では説明不能)
- 音声末尾の欠損(`said`の末尾切詰など、ASRが文脈で補完して綴りだけ正しく返す)
- ASRが文脈(前後clip・prompt)に引きずられた誤転写(プライミング。文脈付きASRはauto-acceptの根拠にしない=C-c REJECTED)
- 音素が実質的に異なるケースまで許容しない。単純な綴り類似度や文脈推測だけでPASSにしない。
- Productionの`protected_check`(数字・否定・保護語)通過後にのみ適用する。通過しない場合は本機構を適用せず既存判定へ。

### 2-7. Standard減速後を含めた全Production経路の整合
- 判定対象6経路: Standard減速前 / Standard 6%減速後 / Advanced / 初回生成 / retry・fallback・regeneration / Local Rewrite後の再検証。
- **減速前だけ先行して減速後への適用を後追いにすることは禁止**。設計・Trialは最初から全経路を含める。
- **減速前と減速後で判定思想が変わらないこと**を受入条件とする(判定を入力=canonical・ASR転写のみの純関数にし、経路・減速の有無を入力に持たない)。
- 既存承認済みの判定仕様が減速後に適用されていない場合は、**未配線(承認済み仕様の配線漏れ)**/**既知スコープ外**/**新規仕様が必要**を明確に区別して記録する(GAP_MAP_01.mdの4区分)。

### 2-8. 将来同じ問題が起きたときの判断方法
下記「4. 将来同じ問題が起きたときの判断手順」に従う。個別の語・個別のtakeへの個別修正の積み重ねで閉じない(PM_GOVERNANCE 14-1)。

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 綴り水準 | ASR転写とcanonicalを文字列(綴り)で比較する判定。現行Pattern A/B/Cはここ。 |
| 音素水準 | 両者を音素列(ARPAbet等)に変換して比較する判定。Equivalence Layerの`phoneme_prefix_drop`、Trial音韻判定がここ。 |
| 連結発音(connected speech) | 語境界で隣接する音が融合・弱化・脱落・同化・再分節する自然な音声現象。 |
| 同音異綴り | 音素列が同一で綴りが異なる語(`Mello`/`Mellow`/`Melo`、`wait`/`weight`)。連結を要さない。 |
| 融合・弱化・脱落 | 同一/類似調音の子音連続(s+s、t+t、d+k、s+sh、t+y等)で、片方が長い1音に融合、または語末子音が弱まる/落ちる現象。 |
| 再分節(resegmentation) | 語境界の子音が隣の語に付く(`survey suggests`→`survey suggest`/`surveys suggest`)、語境界が移動する現象。 |
| 確認済み発音 | CMU辞書(代表発音)、Pronunciation Ledger、ユーザー確認済みの読み。推定(OOVのstem+規則的-s等)は「確認済み」に含めない。 |

## 4. 将来同じ問題が起きたときの判断手順
(PM_GOVERNANCE 14-1の7段階と整合)

1. **検知**: ASR差分でUNCERTAIN/NG/STOPPED/HRになったclipを検知する。
2. **既存機構とのreconcile**(14-1の2段、21節A/B/C分類): Pattern A/B/C、Equivalence Layer、Resolver/Ledger、ASR Semantic Equivalence(er021)、Secondary ASR Cascade Tier3、`_post_slowdown_cascade_rescue`、Local Rewrite 7 Gatesが対象範囲か・なぜ効かなかったか(配線漏れ/入口条件/OOV G2P不在)を先に確認。**重複する新機構を作らず、既存機構の再利用・拡張を優先**。
3. **原因切り分け**: 綴り水準の限界か、音素水準の限界か、入口条件か、未配線か、音声の実体(本当に誤発音)か。
4. **failure mode一般化**: その語・そのtakeでなく、同じ原因構造に属する範囲(全Family・全6経路・固有名詞/一般語)で定義する。
5. **7段構造での診断**(下記5)と**安全条件**(2-6)の確認。既存承認済み許容ルールを**一貫適用**する。
6. **最小Trial**: 評価A(正常音声の誤NG削減)と評価B(異常音声の誤PASS防止、**既存Pattern A比の増分**)の両方。増分>0の方式は採用候補にしない。Trial隔離でProduction無変更、Opus独立レビュー(条件A)。
7. **許容/HRの分岐**: 根拠が不十分なら**無条件PASSにせず**既存の安全な判定・Human Reviewへ。説明付きHR候補にするのは確認時間の短縮であり、HR件数を減らさない。ユーザー判断とProduction採用は人間のみ。

### 5. 診断の7段構造(ユーザー合意)
1. 原文とASR転写の差分を検出する。
2. 差分に関わる固有名詞・一般語それぞれについて、発音を確認する。
3. 確認済み発音辞書・G2P・既存Resolver等を使い、**音素レベルで同等性を評価**する。
4. 同音異綴り / 自然な連結発音 / 融合・弱化・脱落 / 語境界の再分割を**区別して診断**する。
5. 既存承認済みの許容ルールを**一貫して適用**する。
6. 否定・時制・数・重要語の置換や欠落などの**安全条件を維持**する。
7. 根拠が不十分な場合は無条件PASSにせず、既存の安全な判定またはHuman Reviewへ回す。

## 6. Melo / Mello 非対称の扱い
- 現行Productionは`Melo said`(Pattern A)をPASS、`Mello said`/`Mellow said`をUNCERTAIN(HRまたはSTOPPED)とする。同じ音素列(M EH L OW)でも扱いが違う。
- ユーザー原則: 現行Pattern Aの実用的許容を維持しつつ、**同じ音素列として確認できる別綴りには同じ基準を適用する**。同じ現象の一部だけに異なる厳格な証拠基準を課さない。
- ただし既存Pattern Aの誤PASSリスクは安全性検証の対象であり、**「Pattern Aを遡及的に厳格化する」か「同じ基準を同音異綴りへ広げる」かの最終選択は設計草案の範囲外**(Opus条件Aレビュー後にユーザー判断。OPEN-330/339)。

# 固有名詞＋連結発音の判定原則（設計指針・ユーザー合意）
更新日: 2026-10-13

> 本文はユーザーとの議論で合意した**判定の考え方**を記録する。新しい判定ロジックの実装・Trial成功・Production採用の宣言ではない。正式仕様の変更は別途Trial、ユーザー承認、Production Wiring Gateが必要。

## 背景
Family Z『走れメロス』で原文 `Melos said` をASRが `Melo said`、`Mello said`、`Mellow said` などと転写する。現行Pattern Aでは `Melos said` → `Melo said` が綴り一致によってPASSになり得る一方、`Mello said` は通らない。発音上同等な転写を綴りだけで異なる結果にする非対称性が問題。

## 合意した判断原則（重要）
1. **現行許容の理由**: `Melos` 語末の /s/ と `said` 語頭の /s/ が隣接すると融合・弱化・脱落し得る。音声から「どちらの /s/ が消えたか」を必ずしも特定できないが、この**自然な連結発音の構造が成立するなら、実質的に許容**するのが現行Pattern Aの判定思想。個々の /s/ の独立した存在を音響的に証明することは、現行のPASS条件ではない。
2. **同音異綴りには同じ論理を適用**: `Melos said` → `Melo said` を許容するなら、`Mello said` や `Mellow said` が当該文脈で `Melo said` と同じ音素列であることが確かめられる限り、**原則として同じ連結発音ルールで評価するべき**。 `Mellos` など語末子音も保たれた同音異綴りも、確認された読みをもとに評価する。綴りのみの相違を別の発音エラーとして機械的に扱わない。
3. **これは無条件許容ではない**: `Melos` と `Mello/Mellow/Mellos` が単語単体で常に同音だと断定しない。固有名詞の正しい読みとASR側の表記の読みを、辞書・確認済み読み・G2P等で**音素レベル**で照合する。発音の同等性は、単純な綴りの類似や「固有名詞だから」という推測で決めない。例えば `Meros` のように実質的に音素が異なるものは別問題。
4. **推奨する判定の順序**: (a)固有名詞と期待読みの確定 → (b) ASRの同音異綴りを音素ベースで認識・正規化 → (c)語境界の連結発音環境を確認 → (d)既存Pattern A等の受理理屈を**整合的**に適用する。音素の同等性が確認できないものは自動PASSしない。想定外の否定・時制・語置換・欠落などprotected差異を無視しない。
5. **リスクの受け止め方を統一**: 現行の `Melo said` PASS自体が、正常な融合と真の語末/s/脱落を必ずしも弁別できないことを踏まえた実用上の許容判断。新表記のみ別の基準で「独立音響証拠が無いから不可」として矛盾したルールを適用しない。ただし、新しい同等性判定により**追加される誤PASS**は実音声・誤発音・欠落等の反例で検証し、許容安全域を超えないことを確認する。検証なしの自動PASS拡張はしない。
6. **目的は一般化**: `Melos` 固有のallow-listや綴り置換ハードコードではなく、固有名詞＋連結発音に共通する音韻構造を処理できる方式を目指す。

## Standardの減速後判定との一体性
- 承認済み判定ルールはStandardの6%減速後でも同じ原則で適用し、漏れがあれば是正対象。
- 新規判定ロジックをTrial/正式採用する場合、**減速前・減速後を同じ設計と検証範囲に含める**。後追い配線を許さない。
- 初回、retry、fallback、regeneration、減速後再検証の整合、runtime evidenceとRegressionはProduction wiringで必須。

## 並行する検証の位置づけ
- **上流予防Trial**（ユーザーが実施承認）: 歯擦音で終わる固有名詞の直後に歯擦音始まり語を連続させる表現を避けること、およびナレーターの短すぎる attribution clip を避けることを検証する。自然さ・ストーリー性を損なわない。
