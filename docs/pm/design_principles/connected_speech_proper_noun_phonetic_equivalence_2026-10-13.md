# 固有名詞＋連結発音の判定原則（設計指針・ユーザー合意）
更新日: 2026-10-13

> 本文はユーザーとの議論で合意した**判定の考え方**を記録する。新しい判定ロジックの実装・Trial成功・Production採用の宣言ではない。正式仕様の変更は別途Trial、ユーザー承認、Production Wiring Gateが必要。

## 背景
Family Z『走れメロス』で原文 `Melos said` をASRが `Melo said`、`Mello said`、`Mellow said` などと転写する。現行Pattern Aでは `Melos said` → `Melo said` が綴り一致によってPASSになり得る一方、`Mello said` は通らない。発音上同等な転写を綴りだけで異なる結果にする非対称性が問題。

## 合意した判断原則（重要）
1. **現行許容の理由**: `Melos` 語末の /s/ と `said` 語頭の /s/ が隣接すると融合・弱化・脱落し得る。音声から「どちらの /s/ が消えたか」を必ずしも特定できないが、この**自然な連結発音の構造が成立するなら、実質的に許容**するのが現行Pattern Aの判定思想。個々の /s/ の独立した存在を音響的に証明することは、現行のPASS条件ではない。
2. **同音異綴りには同じ論理を適用**: `Melos said` → `Melo said` を許容するなら、`Mello said` や `Mellow said` が当該文脈で `Melo said` と同じ音素列であることが確かめられる限り、**原則として同じ連結発音ルールで評価するべき**。 `Mellos` など語末子音も保たれた同音異綴りも、確認された読みをもとに評価する。綴りのみの相違を別の発音エラーとして機械的に扱わない。
3. **これは無条件許容ではない**: `Melos` と `Mello/Mellow/Mellos` が単語単体で常に同音だと断定しない。固有名詞の正しい読みとASR側の表記の読みを、辞書・確認済み読み・G2P等で**音素レベル**で照合する。発音の同等性は、単純な綴りの類似や「固有名詞だから」という推測で決めない。例えば `Meros` のように実質的に音素が異なるものは別問題。
4. **推奨する判定の順序**: (a)固有名詞と期待読みの確定 → (b) ASRの同音異綴りを音素ベースで認識・正規化 → (c)語境界の連結発音環境を確認 → (d)既存Pattern A等の受理理屈を**整合的**に適用する。音素の同等性が確認できないものは自動PASSしない。想定外の否定・時制・語置換・欠落などprotected差異を無視しない。
5. **リスクの受け止め方を統一**: 現行の `Melo said` PASS自体が、正常な融合と真の語末/s/脱落を必ずしも弁別できないことを踏まえた実用上の許容判断。新表記のみ別の基準で「独立音響証拠が無いから不可」として矛盾したルールを適用しない。ただし、新しい同等性判定により**追加される誤PASS**は実音声・誤発音・欠落等の反例で検証し、許容安全域を超えないことを確認する。検証なしの自動PASS拡張はしない。
6. **目的は一般化**: `Melos` 固有のallow-listや綴り置換ハードコードではなく、固有名詞＋連結発音に共通する音韻構造を処理できる方式を目指す。

## Standardの減速後判定との一体性
- 承認済み判定ルールはStandardの6%減速後でも同じ原則で適用し、漏れがあれば是正対象。
- 新規判定ロジックをTrial/正式採用する場合、**減速前・減速後を同じ設計と検証範囲に含める**。後追い配線を許さない。
- 初回、retry、fallback、regeneration、減速後再検証の整合、runtime evidenceとRegressionはProduction wiringで必須。
