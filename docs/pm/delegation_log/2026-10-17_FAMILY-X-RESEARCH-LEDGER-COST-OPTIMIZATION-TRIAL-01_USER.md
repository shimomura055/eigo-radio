# Claude Code／Fableへの指示
## Family X Research／Fact Ledger コスト最適化比較Trial

**管理ID：FAMILY-X-RESEARCH-LEDGER-COST-OPTIMIZATION-TRIAL-01**

### 1. 目的

Research・Verified Fact Ledgerの費用削減について、品質を維持できる方式を検証する。

Coffee実測ではResearch ¥19.85、Ledger ¥25.14、合計¥44.99。その約89%がWeb検索費用だった。

本Trialでは、コスト削減額だけでなく、**最終的にB3が選ぶストーリーの構成・品質がどの程度変化するか**を重視する。

量産原価目標はStandard＋Advancedの1記事セット当たり¥70。

### 2. 対象・比較方式

**5記事×4方式**を比較する。記事は可能な限り保存済みResearch成果を使用し、ジャンルとFact検証の難易度が異なるものを選ぶ。

| 方式 | 処理内容 |
|---|---|
| 従来方式 | 全Fact検証 → B3選定 |
| 案1 | 全Fact検証（Fact単位の検索上限あり）→ B3選定 |
| 案2 | B3選定 → 選定Factのみ独立検証 |
| 案1＋案2 | B3選定 → 選定Factのみ独立検証（検索上限あり） |

各記事で同じResearch下書きを共用し、比較条件を揃える。

既存の従来方式の成果が比較基準として使用可能なら再利用する。Research・B3・Ledgerの不要な再実行を避ける。

### 3. 案1：検索上限の事前分析

**上限3回は仮説であり、検証済みの最適値ではない。**

有料Trialの前に既存ログをread-onlyで分析し、Factごとに以下を集計する。

- Web検索ツール呼出回数
- 各呼出に含まれる検索クエリ数
- 何回目で十分な裏付けに到達したか
- 最終判定（VERIFIED／AMBIGUOUS／REJECTED）
- 仮に2・3・5回で打ち切った場合の費用とFact喪失リスク

**実際のログで何回目に確認できたかを復元できない場合、推測で成功回数を補わないこと。**

本Trialの暫定上限は**Fact当たりWeb検索ツール呼出3回**とする。ただし、事前分析で明らかに不適切と判明した場合は、理由と代案を提示してSTOPする。

Researchで取得した版・発行年月・出典内該当箇所をLedgerへ引き継ぐ改善も案1の候補だが、検索上限制御とは効果を分離して記録する。既存データから取得できない情報を新たな有料Researchで補完しない。

### 4. 案2：検証不合格時の再選定

重要な確認済み方針：

**選定Factが検証不合格になっても、そのFactを機械的に削除してB3を確定させない。**

例：

1. Research候補：A・B・C・D・E
2. 初回B3：A・B・Cを選定
3. 検証結果：BがREJECTED
4. B3へ不合格理由と既存検証結果を返す
5. B3がストーリー構成を再評価
6. 必要ならD・Eなどを追加選定
7. 新規選定Factを独立検証
8. 最終B3を確定

検証済みFactは結果を再利用し、無駄な再検索を避ける。

AMBIGUOUSとREJECTEDを混同せず、既存の断定禁止・Fact Lockルールを維持する。

**Trial上の安全・費用制御として、再選定は最大2回を暫定上限とする。** 上限に達しても品質を犠牲にしてB3を確定しない。未成立として記録する。

この上限はProduction仕様としての採用判断ではない。

### 5. 5記事の選定

可能な限り次の5タイプを含める。

1. 統計・価格系：Coffee
2. AI・テクノロジー系
3. 社会・制度系
4. 生活・消費トレンド系
5. 複数の出来事や出典が絡むニュース

各記事について、選定理由、保存済みResearch・Ledger・B3の有無、Fact数、検証難度を明記する。

ジャンルの違いだけでなく、統計、出典の版違い、曖昧なFact、時系列、因果関係などの検証難度を分散させる。

Family A／B／Cの停止方針を守り、既存成果を比較材料として参照する場合でも、これらのFamilyのProduction開発・改修は行わない。

### 6. 評価項目

**各方式・各記事について、以下を記録する。**

| 評価軸 | 測定内容 |
|---|---|
| 費用 | LLM／Web検索別の実測額、総額 |
| 検索効率 | ツール呼出回数・クエリ数 |
| Fact品質 | VERIFIED維持、AMBIGUOUS化、REJECTED、誤りの見逃し |
| B3構成 | 採用Fact、主題、展開、結論 |
| B3品質 | 面白さ、一貫性、事実との整合 |
| 再選定 | 回数、追加検証、追加費用、未成立率 |
| 後続工程 | Fact Lock・Risk Flaggerとの整合 |

B3の構成差は、次の3段階で分類する。

- **軽微：** ストーリーの骨格は同じ。
- **中程度：** 骨格は維持されるが、焦点や展開が変化。
- **重大：** 主題・結論・骨格が大きく変化。

構成差の大きさと品質の良し悪しは別々に判定する。

自然な生成ばらつきと方式変更による差を混同しない。重大な差が出た場合、既存証拠で判別できなければ限定的な再現確認を検討する。ただし、追加有料試行は費用Gateの範囲内でのみ実施する。

### 7. 受入条件

Trialの評価では、以下を重視する。

- 採用Factに重大な誤りが残らないこと。
- 既存VERIFIED Factの降格は根拠を伴うこと。
- 不確実なFactを誤ってVERIFIEDに昇格させないこと。
- 最終B3のストーリー品質が維持されること。
- 再選定・追加検証を含む実測総費用で削減効果があること。
- Fact Lock・Risk Flagger等の既存品質要件を満たすこと。
- 一部記事だけでなく、5記事全体の傾向と例外が説明できること。

5記事の結果だけで重大Fact誤りの低頻度リスクまで統計的に否定できるとは扱わない。

### 8. 費用・実施Gate

**既存の費用管理ルールを厳守すること。**

既存成果を棚卸しした後、実行前に以下を算出する。

- 5記事の選定結果
- 各方式で新たに必要なAPI呼出
- 再利用可能な既存成果
- 期待費用・上限費用
- 当日使用済み費用・日次残額

既存のTrial見積（案1：3記事約¥150〜200、案2：3記事約¥55〜60）を、今回の5記事×4方式へ機械的に当てはめないこと。

**新たな有料実行の見積が既存の自律実行許容額を超える場合、ユーザー承認を得るまでSTOP。**

今回のユーザー承認はTrial方針の承認であり、金額未確定の無制限実行許可ではない。

既に十分な実行予算承認が存在する場合は、その適用範囲を確認する。

### 9. Trial専用実装・禁止事項

必要な比較用コード・Promptは、Trial専用として作成してよい。

ただし以下は禁止する。

- Production初回経路の変更
- Production retry／fallback／regenerationの変更
- CURRENT_SPECに未採用案を正式仕様として記載すること
- 新方式を正式Productionへ自動採用すること
- 認められていない有料追加Trial
- 無関係なFamily・機能への変更
- 比較結果を見て都合のよいTakeだけを採用すること

既存コードや保存成果を最大限再利用し、Trialのために本格的なProduction機構を先回りで作らない。

### 10. 報告形式・PM Gate

最初に、**5記事×4方式の比較表**を提示する。

続いて、

1. 案1の推奨検索上限と根拠
2. 方式別の実測費用・削減率
3. 最終B3構成の差（軽微／中程度／重大）
4. ストーリー品質・Fact品質への影響
5. 再選定・追加検証の発生頻度と費用
6. 案1＋案2に相乗効果があるか
7. 70円／記事セット目標への影響
8. Fableによる独立レビュー
9. 各案のTrial終了Status
10. ユーザー判断が必要な事項

Trial終了時は、各案を**REJECTED／VALIDATED／USER_DECISION_REQUIRED**のいずれかに分類する。

**VALIDATEDはProduction採用を意味しない。**

ユーザーが正式採用を決定するまで、APPROVED_FOR_PRODUCTIONへ変更してはならない。

今回のTrial終了後は必ずSTOPし、報告すること。

### 11. Closeout

Trial結果と判断待ち事項を既存のDecision Log／Open Items／ユーザー判断台帳に整合させる。

Production正式初回経路とTrial経路を明確に分け、未承認仕様へのDangling Referenceを作らない。

APPROVED_FOR_PRODUCTIONのまま未配線になっている既存事項について、今回の範囲に影響するものがあれば明示する。

**新方式のProduction配線は行わない。ユーザーの選定・正式採用判断を待つこと。**
