## Task B｜日本語ASR誤判定の原因究明・根本対策

### 目的

**正常な日本語TTS音声がASRの文字起こし誤りによって不必要にNGとなり、再生成・Human Reviewを発生させる問題を根本的に改善する。**

ただし、本当に発音を間違えた音声を誤ってPASSさせてはならない。

対象は今回のタイトルだけではなく、Family X/Zの日本語音声に共通する問題として調査する。Family固有の例外が必要な場合は理由を明示する。

### Phase 1｜原因究明

今回の3回の生成について、実際の音声、TTS入力、ASR転写、判定ログを再検証する。

重点調査事項：

**①「しわ」の問題**

- 正しい「しわ」が「詩」「死」「氏」と認識された理由。
- 日本語ASRで、ひらがな・漢字・同音表記の違いをどのように扱っているか。
- 既存の表記違い・同音救済仕様が日本語にも適用される設計なのか。
- 適用されない場合、その理由は何か。
- 「しわ」と「し」は音として異なるため、実際の音素の欠落を誤って救済しない方法。

**②「8,900本」の問題**

- 数字の音声が正常でも、ASRが「8000」「800本」「8000900本」などと誤変換する原因。
- 数値の正規化・照合処理が妥当か。
- 正しい数字と実際に読み間違えた数字を区別できるか。
- 今回の中核数値保持仕様や既存の数値保護判定との整合。

**③ 既存Production仕様の調査**

- 日本語ASRのPrimary／Secondaryの役割とPASS条件。
- 日本語特有の同音語・表記ゆれ・数詞の正規化。
- TTS再試行・fallback・Human Reviewへの移行条件。
- 過去の同種問題と対策。
- Family X/Zにおける共通化の余地。

今回の3音声をユーザーが問題なしと判定した事実を、原因分析の根拠として利用すること。

ただし、ユーザー試聴PASSだけを理由にASR判定条件を緩めるのではなく、誤判定の原因を特定する。

### Phase 2｜対策立案

原因に応じて、最も効果的で低コストな対策を設計する。

以下は検討候補であり、実装方法を固定するものではない。

- 日本語の表記ゆれ・同音語照合の改善
- 数字・助数詞の音声と文字表記の対応改善
- Primary／Secondary判定の適切な組み合わせ
- 既存の同音救済機構の再利用・拡張
- 本当に発音が違う場合と、ASRの文字変換だけが違う場合の識別

**品質基準を下げてNGをPASSにするだけの対策は禁止。**

誤PASSを増やさず、不要な再生成やHuman Reviewを減らすこと。

既存機構の改善で解決できる場合、新たな独立システムを乱立させない。

### Phase 3｜自律改善Trial

承認済み予算・Trial範囲内で、原因分析→修正候補→検証→再評価のループを自律的に実施する。

- 誤NGの削減と、実際の誤発音を検出する能力の両方を評価。
- 今回の正常3音声を必ず評価対象に含める。
- 過去の日本語ASR不一致例も可能な限り再利用する。
- 正常音声だけでなく、本当に発音が誤っている負例も用意する。
- 既存の承認済み数値・同音・保護語の仕様を壊さない。
- 追加API費用と量産単価への影響を測定する。
- 不必要な有料TTS再生成を避け、既存音声・記録の再利用を優先。
- 独立して進められる調査・評価・実装は並列化する。

改善が見込める限り、単にTrial回数が増えたことを理由に停止しない。

一方、同じ改善案で失敗が続く場合は、原因・前提・手段を再検討し、別アプローチへ切り替える。

必要に応じてOpusレビューで、誤PASSリスク、数値保護との整合、別方式の可能性を独立検証する。

Fableには、Trialの結論と根拠の独立評価を依頼する。

### Phase 4｜再発防止・Production適用判断

有効な対策が得られた場合、以下を確認する。

- Family X/Zのどこに共通適用すべきか。
- 通常生成だけでなくretry／fallback／regeneration／resumeでも正しく動作するか。
- 既存の同音救済・数値保護・Human Review仕様と矛盾しないか。
- 古い不要な検査・例外処理を整理する必要があるか。
- 品質、制作速度、量産単価がどう改善するか。

**Trial成功のStatusはVALIDATEDまで。ユーザーが正式採用を明示するまでProductionへ配線しない。**

正式採用後は、対象FamilyごとにProduction実経路の発火証拠、テスト、SSOT・Git整合まで確認し、PRODUCTION_WIREDを目指す。

## 3. 予算・STOP条件

開発費は原則1,000円／日（JST）を上限とし、既存の個別承認枠も守る。

- 承認済みの予算・Scope内で自律的に実施。
- 新規の有料Trial範囲や予算追加が必要なら、費用・目的・期待効果を示して判断を求める。
- 品質基準やProduction仕様の変更はユーザー承認が必要。
- 重大な品質・安全問題、明示STOP、予算超過見込み、改善見込みのない反復では適切に停止。
- 軽微な不具合は委任範囲内で自律的に修正・再検証し、逐一ユーザーへ判断を求めない。

## 4. 報告形式

### Task A：完成版報告

最終試聴URLと品質検査結果を先に報告する。

### Task B：原因究明・改善Trial報告

次の順番で報告する。

1. **原因**：なぜ正常な音声がNGになったのか。
2. **対策**：何をどう変更すると改善するのか。
3. **検証結果**：正常音声・異常音声で、それぞれ何件PASS／NGとなったか。
4. **QCD**：誤NG削減効果、誤PASSリスク、時間・費用への影響。
5. **Fable／Opus評価**：独立レビュー結果。
6. **Status**：VALIDATED／REJECTED／USER_DECISION_REQUIRED。
7. **必要なユーザー判断**：正式採用の可否など、本当に重要な事項のみ。

Task Aの完了をTask Bの終了まで待たせないこと。
