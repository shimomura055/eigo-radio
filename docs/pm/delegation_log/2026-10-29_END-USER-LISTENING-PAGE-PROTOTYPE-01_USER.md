# End User向け記事視聴ページ｜Phase 1・2 実施指示（改訂版）

## 目的

eigo-radioのEnd User向け記事視聴ページについて、既存デザインを継承しながら最新の承認済み学習コンテンツ仕様を反映した試作を制作する。

今回はPhase 1（現状調査・仕様整理）とPhase 2（動作するデザイン試作）まで進める。

Production正式採用・配線は今回の対象外。Statusは最大VALIDATEDとし、ユーザーの評価・正式採用判断を待つ。

## 1. デザインの基本方針

以下の旧フォームとunifiedプレイヤーを参照する。

- https://shimomura055.github.io/eigo-radio/user_test/articles_2026_0918.html
- https://shimomura055.github.io/eigo-radio/user_test/unified.html

ユーザーは旧デザインのシンプルさを評価している。

全面リニューアルではなく、既存の良い部分を継承し、最新機能を自然に組み込むこと。

対象は記事をクリックした後の視聴ページに限定する。

Topページ・記事一覧・会員機能などは開発しない。

スマホとPCの双方に対応し、特にスマホでの見やすさ・操作性を重視する。

## 2. Phase 1：既存実装・最新仕様の調査

Repo、CURRENT_SPEC、実際の公開ページ、Production実装を確認する。

以下を調査する。

1. 旧unifiedプレイヤーの画面構造・機能・スマホ対応状況
2. 最近制作した完成記事の表示機能
3. Standard／Advancedの最新学習コンテンツ仕様
4. Key Phrase・Wordの英語、日本語意味、英語解説、音声、本文ハイライトの表示仕様
5. Grammar & Sentence Structureの表示仕様
6. Family X/Y/Zそれぞれの再生・記事構成・表示仕様
7. 再生位置とスクリプトを対応付ける既存データ・機能の有無
8. Production初回経路・retry・regeneration・resumeと公開ページの関係

既存仕様、既存実装、未配線機能を明確に区別する。

新規制作せずに再利用できる機能を優先する。

調査は必要十分にとどめ、試作可能な部分は並行して進める。

## 3. Phase 2：記事視聴ページ試作

Family Xの完成記事を1件選び、実際の音声・本文・Key Phrase・解説を利用したページを制作する。

原則として以下を組み込む。

- 記事タイトル・レベル表示
- 全体再生およびパート別再生
- 再生・停止・シークなどの操作
- スクリプト表示
- Key Phrase／Wordの意味と解説
- Grammar & Sentence Structure（対象レベルのみ）
- その他、最新の承認済み表示仕様に含まれる機能
- スマホ・PC双方に適したレイアウト

機能・項目は実際の承認済み仕様に合わせる。既存機能の削除や学習仕様の変更は行わない。

音声品質や学習コンテンツそのものは変更しない。

## 4. 音声連動ハイライトの試作（文章単位）

ユーザー判断により、**音声連動ハイライトはB. 文章（1文）単位を採用する。**

段落単位・単語単位との比較Trialは実施しない。

### 目的

音声再生中に、現在読み上げられている文章（1文）をハイライトし、End Userが音声とスクリプトの対応を直感的に把握できるようにする。

### 実施内容

- 実際の音声とスクリプトを使用して、1文単位のハイライトを実装する。
- 再生位置に応じて、現在読み上げ中の文章を自動的に強調表示する。
- スマホ・PC双方で見やすい表示にする。
- 既存のTTS・ASR・Chunk情報などを活用し、追加費用と処理負荷を最小化する。
- 原則として既存音声を再生成しない。
- Family X/Y/Zの構成差を考慮し、共通利用できる設計を優先する。

### 検証事項

1. 文章の開始・終了とハイライト切替の同期精度
2. シーク・一時停止・再開時の正しい表示
3. パート切替・Chunk境界での動作
4. 長い無音・再生終了時の表示
5. スマホでの視認性と操作性
6. 量産時の追加処理時間・費用
7. 音声再生成・記事更新時の保守性

同期が不正確な場合は、見かけ上動作していても成功扱いにしない。

技術的な問題が発生した場合は、既存仕様・予算・委任範囲内で原因究明、修正、再検証まで自律的に進める。

## 5. QCD

優先順位は品質 ＞ Delivery ＞ 量産単価。

- 既存の承認済み品質・機能を維持する。
- デザインの過剰な作り込みを避ける。
- 既存コード・データを最大限再利用する。
- 独立作業は並列化し、不要な待機・日付分割を行わない。
- 量産単価70円／記事セットへの影響を算定する。
- 有料APIが必要な場合は承認済み予算・Scope内で管理する。
- 新規有料Trialが承認範囲外になる場合は実行前に判断を求める。
- 既存Productionの動作・公開ページを壊さない。

仕様やデザインの未承認変更はProductionに反映しない。

## 6. 成果物

最終的に以下を提出する。

1. Phase 1調査結果：既存機能、最新仕様、差分、再利用方針
2. 新しい記事視聴ページの試作URL（スマホ・PC対応）
3. **文章（1文）単位の音声連動ハイライトが実際に動作する試作**
4. ハイライト導入時の開発負荷・量産費用への影響
5. Family X/Y/Zに展開する際の課題
6. Phase 3でユーザーが判断すべき事項

試作はDEV／Trialとして隔離し、正式公開ページと区別する。

実際のブラウザ表示・操作・音声同期を検証し、未確認項目を明示する。

Fableには独立して、最新仕様との整合、画面機能、スマホ表示、ハイライト同期、QCDを確認させる。

## 7. 完了条件・STOP条件

Phase 1・2の成果物が揃い、ユーザーが試作を操作・評価できる状態になったら完了報告する。

試作の出来が良くてもProduction採用は行わない。

承認外の仕様変更、予算超過、重大な品質問題、Production影響が見つかった場合は該当作業をSTOPし、判断事項として報告する。

最終報告はユーザー判断に必要な結果を優先し、中間の詳細な技術ログは不要。

次のPhase 3に向けた評価・採否判断はユーザーに委ねる。
