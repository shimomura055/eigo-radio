# Claude Code / Fableへの指示
## ASR品質問題2件の根本対策 — 原因究明・包括改善・反復Trial

### 1. 目的・ユーザー決定

以下2件について、**個別対応ではなく、今後の量産で同種の問題が再発しない包括対策**を実施する。

**① 固有名詞の検出・発音救済**

『開いた窓』の `Bertie → Birdie` 問題。

先日承認・Production反映した「固有名詞は発音不一致だけでProduction停止しない」というルールが、発音台帳に未登録の固有名詞には機能していない。

これは個別の台帳登録で済ませる問題ではない。

**固有名詞を認識・分類する仕組み自体を根本から見直すこと。**

**② 英国・米国の綴り違い**

`speciality → specialty` がNGとなり、不要な局所書き換えで `forte` に変更された問題。

正当な英米表記の違いによってNG・不要な再生成・脚本変更が発生しないよう、包括的に対策する。

`speciality/specialty` の個別ペア登録だけで解決しないこと。

### 2. 調査・対策設計

両問題について、以下を実施する。

1. 現行Production経路、ASR判定、発音台帳、既存の同音・異表記救済、retry／rewrite処理を調査する。
2. 過去のTrial・承認済み仕様・既存対策と照合し、今回の問題が発生した根本原因を特定する。
3. Family X／Zに共通適用できる包括対策を設計する。
4. **Opus独立レビューを積極的に活用**し、設計の抜け漏れ、誤PASSリスク、改善余地を検討する。
5. 追加のAPI費用・処理時間を最小化し、量産単価70円／記事セットとの整合を確認する。

固有名詞については、発音台帳への事前登録に依存せず、本文中の固有名詞を高い網羅性で検出できることを目指す。

ただし、固有名詞と認識しただけで、異なる発音まで無条件にPASSさせない。承認済みの発音救済仕様と安全条件を維持すること。

英米表記についても、正当な綴り違いを救済する一方、意味・発音が異なる単語の誤PASSを防止すること。

### 3. Trial・自律改善ループ

**今回最も重要な追加指示。**

Trialを1回実施して期待結果が出なかっただけで、USER_DECISION_REQUIREDとして停止しないこと。

以下の改善ループを、承認範囲内で自律的に回す。

**原因分析 → 対策設計 → Opusレビュー → Trial実装 → 検証 → 結果分析 → 必要なら再設計・再検証**

- Trial失敗時は、失敗原因と改善見込みを分析する。
- 同じ対策の微修正だけでなく、必要に応じて前提・検出方法・判定構造そのものを見直す。
- 見込みのない同一方向のTrialを繰り返さない。
- 過去のTrial結果・既存検証データを再利用し、効率的に検証する。
- 1回のTrialで正常系・異常系・境界条件をできるだけ広く確認する。
- 修正のたびに不要な全面E2Eを実行せず、必要十分な範囲で検証する。
- Opus／Fableを活用して、原因分析・方針転換・検証結果の妥当性を確認する。

**Trial回数を理由に停止しない。**

承認済み予算・品質・安全条件の範囲で、改善見込みがある限り自律的に進めること。

Humanへ戻すのは、合理的な代替手段を検討しても解決の見込みが立たず、実質的に行き詰まった場合、または予算・安全・承認境界に達した場合のみとする。

### 4. 検証・受入条件

**① 固有名詞**

- `Bertie` のような未登録の固有名詞を正しく検出できる。
- 登録済み・未登録の双方で、承認済み発音救済ルールが機能する。
- 人名だけでなく、地名・組織名・作品名など必要な固有名詞カテゴリを確認する。
- 同音・表記揺れ・実際の誤発音を区別し、不適切な誤PASSを防ぐ。
- Family X／Zの既存Production仕様と矛盾しない。

**② 英米綴り**

- `speciality/specialty` 以外の代表的な英米表記差も正しく救済できる。
- 正当な表記差でNG、不要な書き換え、再生成、HR Lockが発生しない。
- 実際に異なる単語・意味・発音を誤PASSさせない。
- ASR Primary／Secondary双方と、既存の同音・異表記救済仕様に整合する。
- Family X／Zの既存品質基準を維持する。

両対策とも、個別事象の解消だけでなく、未知の事例に対する一般化性能を検証すること。

### 5. Scope・承認境界

今回承認する範囲は、**原因究明、包括対策設計、Opusレビュー、Trial環境への実装、必要な反復検証、Fable独立評価まで**。

正式Production仕様の変更・配線は未承認。

- Trial成功時は `VALIDATED` として報告する。
- 新仕様の正式採用はユーザー判断を必須とする。
- `APPROVED_FOR_PRODUCTION` を経ずにProductionへ配線しない。
- Trial用対策を正式経路のretry／rewriteなどから暗黙参照させない。
- 既存Productionや他の進行中案件を不用意に変更・停止しない。

開発費は既存の承認済み日次予算・個別承認枠内で管理し、必要な範囲で自律配分する。

### 6. 最終報告

①②について、それぞれ以下を報告する。

1. 根本原因と既存仕様が機能しなかった理由
2. 採用候補となる包括対策の仕組み
3. Trial結果と改善前後の比較
4. 失敗からの再設計・再検証の履歴と最終到達結果
5. 誤PASS・見逃し等の残存リスク
6. Family X／Zへの適用範囲
7. 制作速度・量産単価への影響
8. Opusレビュー・Fable独立評価
9. SSOT／OPEN_ITEMS／Git記録と最終Status

**品質基準を満たした時点でVALIDATEDとしてTrialを終了する。必要以上の磨き込みや追加Trialは行わない。**

もし実質的に行き詰まった場合は、単に「Trial失敗」と報告するのではなく、試したアプローチ、改善しなかった理由、代替手段、残る選択肢とQCD影響を整理してHuman判断を求めること。

### 7. 『開いた窓』の扱い

今回の2問題を、Bertieの個別台帳登録やspeciality/specialtyの個別例外追加だけで解決済みとしない。

『開いた窓』の停止中音声は保全し、包括対策の検証結果と正式採用判断を踏まえて再開する。

ただし、ほかの独立工程を不合理に止めず、Family X新規2記事・Family Yなどの進行は維持する。

**最優先は、同じ原因によるProduction停止を量産時に繰り返さないこと。そのために必要な自律的な原因究明・再設計・再検証まで責任を持って進めること。**
