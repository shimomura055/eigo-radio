# Claude Codeへの指示｜日本語訳品質アラーム機構の設計・自律Trial

## 1. ユーザー決定事項

日本語訳品質改善 `JA-GLOSS-NUANCE-01` について、以下を正式決定します。

1. **改善案B3はREJECTED（不採用）。** 副作用による既存訳の品質悪化リスクがあるため。
2. **現行の日本語訳生成Prompt・仕様は維持する。**
3. 生成済み日本語訳の自然さ・意味の適切さを、独立してチェックする新しい品質アラーム機構を検討する。
4. 問題が疑われる訳は、Human Reviewページで赤字などによる警告を表示する。
5. ユーザーが警告を参考に、最終承認または修正指示を行う。
6. **品質チェックに使用するモデルはLuna 6.0に限定する。他モデルの採用・比較Trialも行わない。**

目的は、訳生成方式を変えずに、日本語訳の品質問題をHuman Review段階で発見できるようにすることです。

既存の品質基準や選定仕様を変更しないでください。

## 2. 品質目標

**警告の的中率（Precision）80〜90%を目標**として設計・検証してください。

誤警告が多いとユーザーの確認負担が増えるため、特にPrecisionを重視します。

ただし、警告対象を極端に絞って高Precisionを実現し、重大な誤訳を大量に見逃す方式は望ましくありません。

Trialでは以下を別々に測定してください。

- Precision：警告したもののうち、本当に問題があった割合
- Recall：実際に問題がある訳のうち、警告できた割合
- 誤警告件数・内容
- 見逃した誤訳の件数・内容
- 重大な意味の誤りの検出状況
- 記事セット当たりの追加費用

80〜90%は目標であり、Trial前から合格を保証するものではありません。評価結果を正確に報告してください。

## 3. チェック機構の基本仕様

対象は、Key Phrase・Key Wordなど、ユーザーがHuman Reviewで確認する日本語訳です。

独立チェック機構には、必要に応じて以下の情報を与えてください。

- 英語の学習対象表現
- 現在の日本語訳
- 該当表現が登場する英文
- 前後の文章
- 記事全体の文脈
- Standard／Advancedのレベル
- 必要に応じた既存の英語・日本語解説

特に以下の品質問題を検出対象として検討します。

1. 英語表現と日本語訳の意味が一致していない。
2. 文脈上の意味ではなく、一般的すぎる意味で訳している。
3. 比喩・物語上のイメージやニュアンスが失われている。
4. 自然な定訳・専門用語を不適切に言い換えている。
5. 日本語として不自然、冗長、または分かりにくい。
6. 同じ記事・解説内で、意味上重要な訳語の不整合がある。

代表的な検証対象には以下を含めてください。

- `verdict` →「結論」（本文では裁判の比喩。適切な訳は「評決」）
- `things left out` →「省かれたもの」（本文では「出しっぱなしのもの」）
- `culprit` →「原因」
- `charge` →「非難」
- `radius` →「中心から外側までの長さ」

ただし、これらを個別辞書や特定語の例外ルールとして実装しないでください。一般化可能な方式として検証します。

また、これらの訳が常に誤りとは限りません。**本文の文脈に基づき、適否を判断すること**が重要です。

## 4. 対策比較・自律Trial

Luna 6.0のみを使用し、複数のPrompt設計やチェック方式を比較してください。

例：

- 文脈と訳語を直接照合する方式
- 意味の一致と日本語の自然さを分離して検査する方式
- 問題の重大度や確信度に基づいて警告する方式
- 1回のモデル呼び出しで複数項目をまとめて検査する方式
- 必要な場合だけ追加判定する方式

これらは候補であり、Claude自身がより有効・低コストな方式を設計して構いません。

特に、**Precisionを維持しながら、量産単価の上昇を最小限にすること**を重視してください。

品質を落とす単純なモデル変更や、無条件の多重API呼び出しは避けてください。

同一モデルでも、Prompt・入力文脈・判定方式・バッチ処理の工夫で改善できる余地を検証してください。

### Trialの進め方

原因分析 → 複数方式の比較 → 実データによる評価 → 誤警告・見逃しの分析 → 改善を自律的に繰り返してください。

- 既存の正常訳と問題訳の双方を含む検証セットを用意する。
- Family X/Y/Z、Standard/Advancedの違いを考慮する。
- Prompt調整に使っていないデータでも検証する。
- 既存の承認済み品質仕様を変更しない。
- 効果の乏しい方式の反復を避ける。
- 目標に達したら、不要な追加Trialは実施しない。

精度評価に際して、途中で合格基準を緩和してPASSとすることは禁止します。基準未達なら未達として報告してください。

## 5. Human Review画面の想定

今回のTrialでは、実際のHuman Review画面に近い形で警告表示の試作・確認も行ってください。

想定表示：

**Key Phrase：verdict**

現在の日本語訳：結論

🔴 **訳語の確認を推奨**

本文では裁判の比喩が使われているため、「評決」の方が文脈に適している可能性があります。

改善候補：評決

ユーザーは警告を参考に、そのまま承認するか、訳語の修正を指示します。

### UI原則

- 警告は問題が疑われる項目だけに表示する。
- 警告理由は短く、具体的にする。
- 改善候補は有用な場合のみ提示する。
- 警告の有無によって通常の承認操作を妨げない。
- ユーザーが修正しない場合、元の日本語訳を維持する。
- 正常な項目に不要な表示を追加しない。

今回の試作はDEV／Trial専用とし、ProductionのHuman Review画面は変更しないでください。

## 6. QCDと予算管理

最優先は品質ですが、量産単価70円／記事セットの目標を踏まえ、追加コストを厳しく評価してください。

以下を比較・報告してください。

- Luna 6.0の実際のAPI使用量・費用
- 1記事セット当たりの追加費用
- バッチ処理による費用削減効果
- 検査に要する追加時間
- 警告によって増減するユーザーの確認負担
- 既存工程との統合による重複処理削減の余地

**他モデルへの切替によるコスト削減案は不要です。**

検査を実施することで量産単価が増加する場合、その費用に見合う品質改善効果があるか評価してください。

### 予算不足への対応

既存の承認済み予算・Trial範囲内で自律的に進めてください。

追加予算が必要になると予見した段階で、十分な余裕をもって追加予算上限を申請してください。

予算切れ後に「停止していました」と事後報告すること、合理的理由なく翌日の予算回復まで持ち越すことは禁止します。

ただし、未承認の予算上限を超える有料処理は行わないでください。

## 7. Production採用・Status管理

今回承認されているのは、設計・Trial・DEV試作までです。

到達可能Status：

- VALIDATED：精度・副作用・費用・UI試作の検証が完了
- REJECTED：採用に適さない方式
- USER_DECISION_REQUIRED：重要な未解決事項が残る場合

**Production配線はユーザー正式承認まで禁止します。**

Trial終了後、正式採用の判断材料を提示してください。

将来、正式採用が承認された場合には、Family X/Y/ZのStandard/Advanced、Human Review正式経路、retry/fallback/regeneration/resume、runtime evidence、Regression、SSOT/Gitとの整合を確認し、PRODUCTION_WIREDまで追跡することになります。

今回のTrial段階でこれらを無断実装しないでください。
