# Claude Codeへの指示｜Family Z 固有名詞ASR認識改善・Azure Phrase List重み比較Trial

## 1. 目的・ユーザー承認

**目的：Azure Secondary ASRが、記事中の固有名詞を一般語より適切に優先認識できるかを検証し、正しく発音された音声の不要なNG・Human Reviewを減らす。**

対象となる問題：

- 原稿：`Melos drank`
- TTS音声：語末に無声 /s/ が存在することを既存調査で確認
- OpenAI Primary：`Mello drank`
- Azure Secondary：`Mellows drank`
- Azureには既に `Melos` をPhrase Listとして渡しているが、認識は改善しなかった
- 現行のPhrase List重みは明示指定なし

ユーザー承認事項：

1. Azure Phrase Listの重み **1.0／1.5／2.0** を比較するTrialを実施する。
2. 同一条件で複数回試行し、認識結果のばらつきを確認する。
3. 意図的に複数の文脈を作り、重み付けの有効性と副作用を評価する。
4. 必要に応じて新規TTS音声を生成してよい。
5. 必要ならTrial終了時にユーザーが音声を試聴する。
6. **Production設定・発音判定仕様は変更しない。**
7. A案・A'案は引き続きREJECTED。今回のTrialで暗黙に再採用しない。

優先順位は品質（Q）＞Delivery（D）＞量産単価（C）。

## 2. Trial設計の基本方針

**単に同じ音声で1.0／1.5／2.0を各1回試し、「差がありませんでした」で終了しないこと。**

今回のTrialでは、次の3要素を分離して評価する。

- **ASRのばらつき：** 同一音声・同一設定でも結果が変動するか。
- **文脈による変化：** 後続語・文長・固有名詞の出現位置などが認識にどう影響するか。
- **重み付けの効果：** ほかの条件を揃えたとき、1.0／1.5／2.0で認識がどう変わるか。

試行回数は、単に多くするのではなく、効果が識別できるよう合理的に設計すること。

開始前に、既存のASR実装・SDK仕様・Phrase List設定、過去の録音2および関連Trialの結果を確認する。

特に、現行の「重み未指定」が実効的にどの重みに相当するかを確認すること。**1.0が現行設定と同等であることを検証せずに前提としない。**

また、Azureの同一音声・同一設定に対する応答が決定論的で、単純反復では新しい知見が得られない可能性も評価する。

## 3. 比較条件と試行設計

### A. 基準条件

既存の録音2を必須対象とする。

- Phrase Listなし：対照
- Phrase Listあり、重み未指定：現行設定の再現
- Phrase Listあり、重み1.0
- Phrase Listあり、重み1.5
- Phrase Listあり、重み2.0

録音2と同一の音声ファイルを使用し、重み以外の条件を固定する。

結果が同一でも、重み設定がSDK・Azureへ正しく反映されたことを確認する。

### B. 文脈を変えた比較

必要に応じて、新しいTTS音声を作成する。

最低限、次のような条件を含める。

| 条件 | 例 | 検証目的 |
|---|---|---|
| 非歯擦音で始まる後続語 | `Melos drank` | 今回の失敗条件を再現 |
| 歯擦音で始まる後続語 | `Melos said` | 既存の音連結許容条件との比較 |
| 文末 | `It was Melos.` | 後続音の影響を除外 |
| 文中 | `Then Melos walked away.` | 通常の文脈での認識 |
| 複数回出現 | `Melos spoke, and Melos listened.` | 同一固有名詞の繰り返し |
| 長文 | Melosを含む自然な50語以上の文章 | 文脈・文長の効果 |
| 一般語との競合 | Melos／Mello／Mellowsと紛らわしい音を含む文 | 過剰な固有名詞認識の検出 |

例文は検証用の候補であり、自然さと音声の妥当性を確認して調整してよい。

重要なのは、**認識してほしい固有名詞を含む正例だけでなく、本来Melosと認識してはいけない負例も設けること。**

### C. 反復と追加試行

同一音声・同一設定について、まず複数回実行して結果の安定性を測る。

推奨初期構成：

- 既存録音2：各条件3回程度
- 文脈別の新規音声：少なくとも各重み条件2〜3回
- 差が出た条件・結果が揺れた条件を重点的に追加反復

ただし、回数は固定しない。

同一音声で全く揺れず、追加反復の情報価値が低い場合は、音声・文脈・話速・発音条件の異なるサンプルを増やす方向に切り替える。

一方、1回だけの偶然の差で効果があったと判断しない。

**試行回数・対象文脈・比較方法を実行前に設計・記録し、結果を見て都合のよい条件だけ採用することを防ぐ。**

## 4. 評価項目

### ① 認識改善

各条件で、以下を記録する。

- 原稿
- 音声ファイル・Voice・Style・話速
- Phrase List内容・重み・SDK設定
- Azureの生転写結果
- `Melos`の正しい認識回数・割合
- `Mello`／`Mellows`などへの誤認識回数
- 同一条件での結果のばらつき

### ② 誤認識の副作用

重みを高くすると、実際には別の単語を発音しているのに、Azureが `Melos` と出力する可能性がある。

これを必ず検証する。

特に、正例での改善と負例での誤認識増加を別々に示すこと。

**固有名詞の認識率が上がっても、実際の誤発音を見逃すリスクが増えるなら、単純に成功と判断しない。**

### ③ 品質判定への実効性

ASR転写の改善だけでなく、既存のProduction判定ロジックに通した際に、

- NGがPASSへ変わるか
- PASS_WITH_WARNINGになるか
- TTS retryやHuman Reviewを回避できるか
- 本来NGとすべき音声を誤PASSしないか

を確認する。

判定ロジック自体は変更しない。

### ④ QCD

- Azure追加呼出回数・実費
- TTS生成回数・実費
- 条件別の処理時間
- 量産時の追加費用見込み
- 品質改善と副作用のバランス

70円／記事セットの量産原価目標への影響も示す。

## 5. 実行・STOP条件

承認済みTrialの範囲内で、自律的に比較条件・試行順序・反復回数を最適化する。

- API費用を抑えるため、既存音声・キャッシュ・既存研究成果を優先利用する。
- 独立した比較や分析は並列化する。
- 結果が出なければ同じ条件を機械的に繰り返さず、何が識別できていないかを分析し、別の文脈・音声へ切り替える。
- すでに品質上十分な結論が得られたら、過剰な追加Trialを行わずCloseoutする。
- 日次開発予算1,000円、個別承認枠および既存STOP条件を遵守する。
- 今回の承認はTrial実施と必要なTTS生成に限る。Production採用や品質基準変更の承認ではない。

ユーザー試聴が必要と判断した場合は、音声と原稿・認識結果を比較できるシンプルな試聴ページを用意する。

## 6. Trial終了時の報告・採否評価

Fableは以下を独立評価する。

- 重み設定が実際にAzureへ反映されたか。
- 複数回・複数文脈の比較が十分で、偶然と傾向を区別できているか。
- 認識改善が確認されたか。
- 負例で誤認識の増加がなかったか。
- Azureの生転写だけでなく、既存Production判定を改善できたか。
- 結果が特定のVoice・文脈に限定されていないか。
- QCDと量産適用時のリスクは妥当か。

最終報告では、必ず以下を示すこと。

1. **結論：Phrase Listの重み調整は有効か。**
2. 重み1.0／1.5／2.0の条件別認識率。
3. 文脈別の効果と、同一条件でのばらつき。
4. 誤認識の副作用。
5. 今回の録音2における改善結果。
6. Production判定・Human Review削減への実効性。
7. QCD・実費。
8. Trial成果物・証拠・Git／SSOT反映。
9. 推奨案および必要なユーザー判断。

**Trial StatusはREJECTED／VALIDATED／USER_DECISION_REQUIREDのいずれかでCloseoutする。**

VALIDATEDでもProduction採用は自動で行わない。

特に、1.0と2.0に差が出なかった場合でも、単に「差がなかった」と報告するのではなく、

- 条件が簡単すぎて差が出なかったのか
- Phrase Listがほとんど効いていないのか
- 既に1.0で十分効いているのか
- 文脈・音声品質によって効果が変わるのか
- 実用上、重み調整では解決できないのか

を、得られた証拠に基づいて整理すること。

**最終目的は、特定の重みでMelosを一度正しく認識させることではなく、一般的な固有名詞の誤認識を減らし、不必要なTTS再生成・Human Reviewを削減できるか判断すること。**
