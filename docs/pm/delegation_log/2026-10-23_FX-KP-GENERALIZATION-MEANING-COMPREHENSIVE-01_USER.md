# Claude Code / Fableへの指示
## Family X Key Phrase品質改善 — 一般化・意味説明の包括対策【修正版】

### 1. ユーザー指摘と是正方針

記事B「英国の電車マナー」のKey Phraseで、以下の品質問題が発生した。

**現行出力**
- Advanced：`draw that line` — to decide where the limit is between what is acceptable and what is not
- Standard：`draw that line` — その線を引く

**期待する出力例**
- Key Phrase：`draw a line`
- Standardの日本語意味：`境界線を設ける`
- Advancedの英語説明：`to establish a clear boundary or limit`

この例で重要なのは、次の3点。

**① Key Phraseを一般化する**

本文中の表現が `draw that line` や `drew a line` であっても、学習用Key Phraseとしては `draw a line` と提示する。

本文の時制や、文脈固有の指示語・所有格などを、そのままKey Phraseへ持ち込まない。

ただし、すべての表現を機械的に原形へ変換するのではなく、英語として自然で、元の意味を保った再利用可能な一般化形を選ぶ。

**② 本文中で使われている意味を正しく捉える**

`draw a line` は、今回の記事では物理的に線を引く意味ではなく、許容範囲などについて境界を設ける意味。

本文の意味を無視した逐語訳は不適切。

**③ 英語学習者向けに意味を一般化する**

記事固有の状況に引っ張られすぎず、別の場面でも通用する意味・説明を提示する。

日本語意味は、今回の例では **「境界線を設ける」** とする。

これは「意味を複数併記すべき」という指示ではない。**原則として、本文で使われている中心的な意味を、簡潔かつ適切に1つ提示する。**

Advancedの英語説明についても、同じ意味を学習者が理解・応用できる自然な英語で表現する。

### 2. 原因究明

既存ProductionのKey Phrase選定・一般化・意味生成・検査工程を調査し、以下を特定する。

- `draw that line` が一般化されずに採用された原因
- Advancedの説明が記事文脈に引っ張られた原因
- Standardが慣用的な意味を捉えず、逐語訳になった原因
- 既存の承認済み一般化ルール・Prompt・Validatorが、なぜ今回の出力を防げなかったのか
- Standard／Advanced間で意味解釈が一致しない構造的原因
- 過去の同種問題・Trial・承認済み対策との関係

特に、既存仕様に一般化の指示があるにもかかわらず機能していない場合は、単純に同じ指示を追加するのではなく、なぜ実効性がなかったのかを明らかにすること。

### 3. 包括対策の設計

次の品質を安定的に実現する仕組みを検討する。

**① 一般化**

冠詞・代名詞・時制・指示語などを適切に処理し、学習者が再利用しやすい自然な基本形を提示する。

一般化によって元の表現の意味や自然さを損なわないこと。

本文に存在する表現を選ぶという既存ルールと、学習用に一般化するルールを両立させること。

**② 文脈に合った意味**

本文で実際に使われている意味を正しく解釈する。

複数の意味を持つ表現であっても、当該文脈に対応する中心的な意味を選ぶ。

**③ 汎用性**

記事固有の状況説明にとどまらず、別の場面でも使える意味・解説にする。

ただし、一般化しすぎて意味が曖昧にならないこと。

**④ 慣用表現**

慣用句・定型表現は、単語ごとの直訳ではなく、フレーズ全体の意味を正しく説明する。

**⑤ レベル間整合**

Standardは日本語意味、Advancedは英語説明という既存仕様を維持しながら、同じ表現に対する意味解釈の整合性を確保する。

**⑥ 意味説明の簡潔さ**

原則として中心的な意味を1つ、必要十分な長さで提示する。

複数の訳語を並べることを品質向上と誤認しない。

既存の承認済み品質基準を維持し、不要な新規ルールや検査工程を増やさないこと。

### 4. Opusレビュー

包括対策の設計について、Opusによる独立レビューを積極的に活用する。

特に以下を確認する。

- 一般化の過不足
- 文脈に合った意味の保持
- 慣用表現の誤解釈リスク
- Standard／Advanced間の意味の整合性
- 既存仕様・過去Trialとの整合
- 過剰なPrompt制約による副作用
- 品質を維持しながら、より単純・低コストに実現できる方法

レビュー指摘は重要度とQCD影響を評価し、必要十分な対策へ反映する。

### 5. Trial・自律的な改善ループ

**1回のTrialが失敗しただけで停止しないこと。**

以下のループを、承認済み範囲内で自律的に実施する。

原因究明 → 対策設計 → Opusレビュー → Trial実装 → 検証 → 結果分析 → 必要なら再設計・再検証

検証対象には、今回の `draw a line` だけでなく、過去のKey Phraseから一般化・慣用的意味・文脈解釈が難しい事例を複数選定する。

**主な検証項目**

1. 本文中に存在する表現を正しく起点としているか
2. Key Phraseが5語以下か
3. 時制・冠詞・指示語などが適切に一般化されているか
4. 本文での意味を正しく捉えているか
5. 記事固有の意味説明に偏りすぎていないか
6. 逐語訳によって本来の意味を失っていないか
7. Standard／Advancedの意味解釈が整合しているか
8. 既存の正常なKey Phraseに副作用がないか

**Trialで問題が残った場合**

- 検証結果から失敗原因を分析する。
- 必要に応じてOpusで再レビューする。
- Prompt・工程設計・判定方法などを再検討する。
- 改善案を再設計し、再Trialする。
- 同じ方向の効果のないTrialを漫然と繰り返さない。

Trial回数だけを理由にSTOPしない。

品質目標に到達するまで、改善見込み・予算・安全条件を考慮して自律的に改善ループを回す。

実質的に行き詰まった場合、または予算・仕様承認などの境界に達した場合に限り、原因・試行結果・代替案・QCD影響を整理してユーザー判断を求める。

品質基準を満たした時点でTrialを終了し、不要な追加Trialや過剰な磨き込みは行わない。

### 6. QCD・既存仕様との整合

- Family X／Zの共通仕様として適用可能な部分を整理する。
- Family固有の事情があれば明確に区別する。
- 既存のKey Phrase選定仕様、語数制限、ASR・音声化、retry／fallbackなどとの整合を確認する。
- 新規のLLM工程やAPI呼出を安易に追加せず、既存Prompt・工程の改善を優先する。
- 不要になった旧ルール・旧検査がないか確認する。
- 量産単価70円／記事セットへの影響を最小化する。
- 独立した作業は並列化し、品質を守りながら完成までの時間を短縮する。
- 既存の承認済み日次予算・個別承認枠を守る。

### 7. 承認範囲・Status

今回承認するのは、以下の範囲。

- 原因究明
- 包括対策の設計
- Opus独立レビュー
- Trial環境への実装
- 必要な反復Trial・再設計・再検証
- Fable独立評価
- Trial結果・意思決定事項の記録

**正式Productionへの新仕様の配線は未承認。**

Trialで成功した場合は `VALIDATED` とし、正式採用はユーザー判断を必須とする。

未承認の仕様をProduction初回経路、retry、fallback、regenerationなどへ無断で配線しないこと。
