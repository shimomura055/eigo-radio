## 2. 測定項目(8指標)

基準値は診断書から取れるものを記載(出典付き)。「Phase 0」=現状の遡及計測が必要。

### M1 不要なユーザー判断依頼の件数
- 定義: ユーザーに出された判断依頼(UDR)のうち、Decision Policy(`RECOMMENDED_PROJECT_DEFINITION_01.md` §4)に照らして**AIが決められた/出自が無い**もの。
- 測定: 全UDRに出自ラベルを付け(Phase 0は遡及、以後は起票時に必須)、出自なし/出自不一致を「不要」とする。ラベリングは、起票者でない独立者(Opusまたは別context)がサンプル確認。
- 基準値: 診断書がUDR #47〜#58(12件)のうち**#53・#55・#56・#57・#58(5件)**を「誤用または Fable判断可能」と指摘(診断書§4 R21)。不要率 約42%(5/12)。ただし診断書の分類であり独立判定は未実施(Phase 0で確認)。UDR_REGISTER全体は実58行(見出し35件・集計55/51件とずれ、診断書§1-2)。
- 目標: 出自なしUDR 0件。不要UDR 月1件以下。
- 期間: Phase 2の全期間(3〜4週)+Phase 3。

### M2 自律的問題解決率
- 定義: 検出した不具合のうち、ユーザーの技術的な指示・是正なしで、承認済み範囲の是正〜確認まで到達した割合(分母=Phase 2で扱った不具合・改善件数)。
- 測定: state_gateの履歴+ユーザー指示ターンの記録。「ユーザー是正」=ユーザーが進め方を指示し直した発言。
- 基準値: T1〜T6のうち、ユーザーが明示的に是正指示した事例は少なくともT3(原因調査の要求)、T4(開発側自律の指示)、T5(通常再生成費用の判断不要の指示)の3件が確認できる([事実]、診断書§2、COMPLETION-01_01 §4)。分母の全体は**Phase 0で測定**(暫定: 6件中3件以上=自律完結率50%以下)。

- 期間: Phase 2。

### M3 原因分析の深さと正確性
- 定義: (a)深さ=`root_cause_dossier`の必須項目(再現証跡/仮説2件以上と事前予測/census分母/原因除去か症状抑制か/副作用)の充足率。(b)正確性=原因判定が事後に覆った率(後続の調査で原因が別と判明、または対策後に再発)。
- 測定: (a)`docs_lint`のdossier検査、(b)独立判定者(Opus)の事後サンプル+再発の有無。
- 基準値: (b)の覆り事例が診断書に少なくとも2件: OPEN-349の件数が「18件」→「7パターン/13ファイル」に訂正(OF-207)、OPEN-310が人称代名詞の枝に限定され、同系統のRule7 INVALIDが4連続した後にcensusで過去13ファイル/7パターンが判明(診断書§2 T1)。分母は**Phase 0で整理**。
- 目標: (a)必須項目の充足100%、(b)覆り率10%以下(ただしn<10では参考値)。
- 期間: Phase 2。

### M4 対策Trialの副作用検出率

## 3. Phase計画

### Phase 0: 現状計測(約3日、JPY0)
- 内容: 上記8指標と補助指標の基準値を、既存の記録から**read-onlyで**遡及計測する。UDR #1〜#58への出自の遡及ラベリング(独立者のサンプル確認つき)、delegation_logから管理IDあたり委任回数・リードタイム、transcriptsからトークン集計、直近の不具合(T1〜T6を含む)のdossier的な再整理。
- 成果物: 基準値表(各指標の値と分母、測定方法の再現手順)。
- 終了条件: M1〜M8のうち少なくとも6指標に基準値が付く。残る指標は「基準値なし」と明記し、Phase 2で前後比較でなく絶対値で評価する。
- 変更なし: 規則・Agent定義・SSOT・Production。

### Phase 1: 文書統合+仕組みの最小セット(1〜2週間、JPY0)
- 前提: ユーザーが案D(または修正案)の採用とPhase 1の範囲を承認。実ファイルの変更は**別管理ID**で行い、変更ごとに通常のPM Gate・Opus独立レビュー(条件A)を通す。
- 内容(優先順):
  1. 文書側の中核(効果が大きい、診断書R1/R3/R4/R20): Decision Policyの規則ファイル昇格、sonnet-worker.md/sandwich-pm.mdの「UDR文化」撤回と責務追加、自律権限基準の単一化。同時にPM_BRIEFのCharter化、固定ブロックのagent定義への移管、PM_GOVERNANCEの履歴分離。
  2. 仕組みの最小セット: (a)`docs_lint`(UDR出自、常駐文字数、OPEN行、dossier必須項目)、(b)`stop_check`(構造化STOP_NOTICE。まずM1 evidence runnerのmock/dry-runで検証)、(c)`state_gate`(3状態+試行計数)、(d)`budget_gate`(run上限、dry-runのみ)、(e)報告マーカーhook。
- **導入は2段階**: 最初の2週は**警告モード**(違反を記録し、ブロックしない)で誤検知率を測り、基準(誤検知が実作業を止めない)を満たしてから**ブロックモード**へ。誤検知による停滞を避けるため。
- 終了条件: 文書の文字数目標の達成(Fable起動時18,000字以下)、各ツールのテスト(既知違反サンプルの検出)PASS、警告モードでの誤検知率の記録。

### Phase 2: 小規模案件での試行(3〜4週間)
- 候補案件(§4)から3〜5件を、新方式で実施する。各案件で、ユーザーは**目的と期待仕様を示すだけ**とし、進め方は指示しない(進め方の指示が必要になった回数がM7)。
- 各案件でM1〜M8を記録。dossier、状態ファイル、費用記録をそろえる。
- 並行案件の合計が同時にユーザー確認を要さないよう、判断待ち項目は非ブロッキングで進める(Decision Policy §4-2の運用ルール2)。
- 週次で中間確認(指標の暫定値、警告モードの違反記録、誤検知)。

### Phase 3: 評価(約1週間)
- 8指標の基準値(Phase 0)と実績(Phase 2)を比較し、§5の基準で「継続・修正・撤退」を判定する報告書を作る。
- 強制の**有効性監査**: 既知違反サンプル(T1〜T6)がhook/validatorで検出されるか、ブロック回数でなくカバレッジで評価(事例20)。
- 正式採用はユーザーが決める。本計画の成功は「採用推奨」でなく「判断材料の提示」までを意味する。

## 5. 撤退・修正条件

### 5-1 即時中止(安全)— 1件でも該当したら導入を止め、原因分析してからユーザーへ報告
1. Gate(Audio Validation/Rule7/M3/ASR)の迂回、またはSTOPセンチネル/STOP_NOTICEの回避・削除。
2. ユーザー承認なしに`APPROVED_FOR_PRODUCTION`または`PRODUCTION_WIRED`が付与された。
3. 未承認のProduction変更、またはハード上限を超えた有料API実行。
4. 本番記事・音声が意図せず生成された。

### 5-2 修正(Phase 3の判定、いずれかに該当)
1. 仕組みの誤検知が実作業を止め、警告モードから抜けられない(誤検知の定義と許容率は、Phase 1の警告モードの記録を見て決める)。
2. 1つの指標が悪化(M1・M2・M5が基準値より悪い、M6が+30%超)したが、安全指標は問題なし → 原因となった要素のみ修正し、Phase 2を延長する。
3. 強制の有効性監査で、既知違反サンプルの検出率が低い → 該当hook/validatorを修正。

### 5-3 撤退(Phase 3の判定、**すべて**に該当、または5-1に該当)
1. M1(不要UDR)が基準値の70%超(ほぼ減らない)かつ M2(自律解決率)が50%未満。
2. 費用(M6)が基準値の+30%超かつ品質指標(M3・M4・M8)が改善しない。
3. ユーザー対応負荷(M7)が基準値より増える。
- 撤退手順: Phase 1で導入した仕組みを警告モードに戻す(または無効化)。文書の変更はgitで履歴が残るため、PM_GOVERNANCEの履歴分離と`CLAUDE.md`の変更は元に戻せる。削除した旧文書は履歴ファイルとして残す方針(SSOTの物理削除はしない、`RECOMMENDED_PROJECT_DEFINITION_01.md` §14)。

### 5-4 注意
- サンプルが小さいため、数値の差は「方向性」として扱う。指標が基準に届かなくても、原因が測定設計の問題であれば、撤退でなく測定の修正とする。
- Phase 2の成否は、AI側の運営だけでなく、**ユーザーが進め方を指示しない期間を確保できるか**にも依存する。M7に影響するため、介入が必要になった回数と理由を記録する。
