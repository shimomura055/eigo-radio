# DESIGN_OPTIONS_01(Phase 1(c) 文脈方式の比較表。判定は書かない、2026-10-31)

共通前提: Production Prompt本文(`TRANSLATE_HEAD`等)は一切変えない。変わるのは「文脈欄に入れる英文のlist」だけ(Production `build_translate_prompt(targets, context)` が既に受け取れる引数)。文脈は全て**決定論**(別AI検査・LLM抽出なし)。ラベルは現行どおり「同じパートの他の文」(文言がずれる点はTrial後の採用検討事項)。実装=`tools/ctx_methods_02.py`(Trial専用、Production非接続)。日本語文(StdのJapanese Preview等)は文脈から除外。単価/換算=`tools/ctx_cost_estimate_02.py`、probe実測0.25token/英字・input 16円/1Mtoken。

## 方式
- **A 現行**: 文脈は同一partの非対象文のみ=新規生成では空。
- **B +直前Part**: 直前の英語partの全文(story/comment/preview/oneline)。
- **C +前後関連文**: 記事内(同level)の線形順で、対象partの直前3文+直後2文(part境界を跨ぐ)。
- **D +記事全体**: 同level内の対象part以外の全英文+記事タイトル(`topic_en`)。
- **E 必要文脈のみ(決定論抽出)**: 記事タイトル+対象partに現れる内容語(4字以上、ストップ語除外、記事内df≤8の希少語)を共有する他part文をidf合計で上位6文+直前2文、記事順に並べる。同一表現の他出現文を拾う=`left out`のようにpartを跨いで語義が決まる表現・同一語の訳語整合・代名詞の指示対象(近傍)をねらう。
- **F(Claude案、E+参照対訳)**: Eの抽出文のうち、**既存の日本語訳があるもの**を対訳で添える(X/Yの承認済み訳[段落対応]、Zは同記事で先に生成・採用済みのpartの訳)。ねらい=訳語整合(city=都/街/町、sister=妹)。Z前partの訳を使う場合はpart生成順への依存とキャッシュ鍵(前part訳のhash)が必要。混入リスク最大(既訳の語が無関係な文へ移る・誤訳の伝播)。**Phase 1ではTrial対象候補に挙げるのみ**(下記の判断基準でE等が訳語整合を改善しなかった場合のStage 2で実測)。
- 直交因子 **V(verifyへの文脈)**: 現行verifyは文脈なし。probeで、文脈で正しくなった訳をverifyが落とす現象を確認(CURRENT_STATE_01 §3)。Trial armとして「verify promptの冒頭に同じ文脈ブロックを付ける(判定基準の本文は不変)」を A以外の有望方式に1回だけ追加比較する。Trial限定。Production採用は別途ユーザー承認(verify入力の変更)。

## 観測された要点(判定ではなく事実)
1. 追加inputだけの費用は最大(D)でも1記事セット0.1円=量産単価70円の0.15%。**費用リスクの本体は再試行率**(verify不合格→再翻訳でcallが2倍、probeでB 3.5倍費用、D 4.2倍)と、fail-closed(英語のみ表示)の増加。
2. 方式Aでも、独立生成のたびに語義・訳語が揺れる(probe: Aの『音』『街』/B・Dの『響き』『都』)。文脈の量で揺れが消えるとは限らない。
3. 文脈を増やしても verify が文脈なしなら、**効果が打ち消される**(B)。
4. 新規構造の設計(文脈の決定論抽出・キャッシュ鍵・verify入力)=PM_GOVERNANCE 11-3条件A該当。Production採用提案前はOpus独立レビュー対象(Trial後、採用提案時に実施)。
