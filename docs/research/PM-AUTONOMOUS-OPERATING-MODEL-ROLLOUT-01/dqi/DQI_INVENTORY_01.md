## 1. 問題1〜5の実例と「規則が効かなかった理由」

## 3. 選択肢の比較

### 3-1 観点ごとの基本判定(C-3の最初の3観点)

- **現行Prompt/規則の文言改善だけで足りるか**: 足りない可能性が高い(Sonnet評価)。是正A/B(文言)は判定行動を改善した(OAR2:14: 原文逐語引用0/3→3/3、設計準拠依存3/3→0/3、実成果物確認0/3→3/3)が、c3(統合失敗)・c2(提示制限)が残った(OAR2:12、OAR2:11、OAR2:13)。残存欠陥は「規則文の不足」というより「(4)→(5)→要約→是正範囲→提示可否の整合」であり、文章規則だけでは盲検で再現した。ただし欠陥n=2・陰性n=1の少数事例(OAR2注記)。
- **構造化した受入判定が必要か**: 問3・5には有効性が高い(c3型は「重大NGが真なら、判定主因/是正範囲/要約に反映」を強制できる)。問1・2・4には直接効かない(UDR発行側の手順が別途要る)。
- **機械的Validatorが必要か**: 欄間の内部矛盾のみ検出可能。意味反転そのものや重大度の付与は検出できない(Fable/Opusの判断が前提)。固定スキーマ化(案ii)が前提で、案(iii)単独では対象ファイルが存在しない(5章)。

## 5. Validator案の実現性

**前提の欠落**: 実運用のFableの`受入記録:`が永続ファイルに固定保存される場所が定義されていない。Grep `受入記録:`は`docs/pm/delegation_log/*.md`(委任文内の指示)、`docs/pm/RESULT_PACKET_*.md`(Sonnet側)、`CP7`などに散在し、`ACTIVE_TASK.md`/`RESULT_PACKET.md`は一時ファイル(`CLAUDE.md`記載)。盲検ではRepo外`SESSION_SUMMARY.md`。→ (iii)は(ii)の固定保存先を前提にする。

**固定欄の例**(スキーマ案):
- `受入記録:` + (1)〜(5)(現行5項目、SPM:70-74)
- (4)内の行ごとに `ID | 要件(原文引用:file:line) | 判定(一致/部分不一致/不一致) | 重大度(CRITICAL=意味反転・Fact欠落・学習内容不一致/MAJOR/MINOR/FORM) | 証拠(file:line)`
- `重大NG:` あり(ID列挙)/なし
- `総合判定:` ACCEPTED / CONDITIONALLY_ACCEPTED / NOT_ACCEPTED
- `判定主因:` (4)のID
- `反実仮想:` 「主因を除いたら判定が変わるか」はい/いいえ(v3提案⑥)
- `是正対象:` ID列挙
- `ユーザー提示可否:` 可 / 不可 / 例外(K1〜K5の充足記述)

**機械検査ルール案(R-A〜R-G)**:
- R-A: 重大NG≥1 → 総合判定がACCEPTEDでない
- R-B: (4)にCRITICALが存在するのに判定主因のIDがCRITICALを含まない → WARN(c3型: 主因がREPORT誤記=FORM、OAR2:92)
- R-C: 重大NG≥1 → 是正対象に全CRITICAL IDが含まれる(含まなければ「受容」旨が明示)(c3: 是正が「再生成禁止」でMAJORが対象外、OAR2:92)
- R-D: 重大NG≥1 → ユーザー提示可否=不可(例外時のみK1〜K5記述必須)(c2型: OAR2:73)
- R-E: (1)に`file:line`形式の引用が0件、または「原文未取得」なのにACCEPTED → FAIL
- R-F: 総合判定ACCEPTEDで(3)の`file:line`が0件 → FAIL
- R-G: 3行要約に「目的適合=一致」とあるのに重大NG≥1 → WARN(自然言語grepのため精度低)

**c3型の検出限界**: c3の最終ラベルは既にNOT ACCEPTED(OAR2:12)でR-Aでは検出できない。R-B(判定主因)・R-C(是正範囲)・R-G(要約)で初めて検出できる。提案③「詳細は重大NGなのに総合ACCEPTED」型(R-A)は、初回CRBの「条件付き受入」ラベル(REBLIND §0)に近い。
**検出できない型**: 重大度の付与そのもの(意味反転をMINORと書く)、証拠の真偽、原文引用の正確さ。これらはFable/Opusの判断領域(GOV:283)。

**実装形態**: `docs/pm/tools/check_delegation_prompt.py`(455行。`normalize_for_match` L58、`find_section_text` L75、`run_check` L297、`main` L422。終了コード常に0=非ブロッキング、JSON出力、test 254行)の**拡張は不適**(責務が委任文検査で、受入記録の欄形式が別。既存testに影響しうる)。新規scriptを推奨(Sonnet所見)し、`normalize_for_match`・JSON出力様式・非ブロッキング運用を流用。見込み: script 150〜250行+test 100〜150行、Sonnet1委任で半日未満(推測)。
**運用上の注意**: 非ブロッキング(記録用)か、rc≠0で受入記録の確定を止めるか。後者は機械的Gateであり新規ユーザー承認事項になりうる(Fable判断)。
