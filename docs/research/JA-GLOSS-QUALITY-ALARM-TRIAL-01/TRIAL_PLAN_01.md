## 2. 測定項目(別々に報告する)

| 指標 | 定義 | 注意 |
|---|---|---|
| Precision | 警告したもののうち、本当に問題があった割合=TP/(TP+FP) | **3つの母集団で別々に報告**: (P-a)実データ候補プール(下記§2-1、実際の有病率)、(P-b)ラベル付きセットの全問題(T1+T3) vs 正常(T2+裁定済みT4)、(P-c)ラベル付きセットの実データのみ(T1 vs T2+裁定済みT4、合成T3を除く)。Wilson 95%区間つき |
| Recall | 問題のある訳のうち警告できた割合 | T1+T3、T1のみ、T3のみで別々。ラベル付きセットでのみ測れる(プールは未ラベルのためRecall不明) |
| 誤警告 | 件数・内容(正常に警告)。FPR(正常中の警告率)もWilson区間つきで | 内容は項目ごとに記録し分類(好み的指摘/文脈誤読/過剰一般化など) |
| 見逃し | 件数・内容(問題に警告なし)。severity別 | T1の見逃しは全件個別に記録 |
| 重大な意味の誤りの検出 | severity=major の問題項目(T3の大半+T1のmajor)の検出率 | §3 ガード条件 |
| 確認負担 | 警告件数/12候補(プール)。1記事セットあたりの警告数 | Precisionとは別。ユーザーが見る件数 |
| 追加費用 | 実測token×単価。1記事セット(Std+Adv)換算、方式別 | ledgerで記録。バッチ化効果(M1対M2)も実測 |
| 処理時間 | call別・段別の実測秒、1セット換算 | |
| 再現性 | 同一入力3回の警告一致率(flip率)。特に正常項目 | 3回のばらつきでPrecisionの揺れを見る |

### 2-1. 有病率の問題(最重要の設計注意)
ラベル付きセットは問題が30/115=約26%と高く、**実運用の有病率(推定3〜10%、未確定)ではない**。Precisionは有病率に強く依存する(P=πr/(πr+(1-π)f)。r=Recall、f=FPR、π=有病率)。例: r=0.8のとき80%を満たすために必要なFPRは π=3%で0.6%以下、5%で1.0%以下、10%で2.2%以下、20%で5%以下。**ラベル付きセットのPrecision(P-b)だけでは、運用でのユーザーの『的中率』を過大評価する**。
対応: 実データ候補プール=`user_test/selection_form_v3/data/*__prod.json`の27ファイル・261候補(X 144・Y 41・Z 76、実際にHR画面へ出た12候補/level)を**未ラベルの運用データ**として検査し、警告が出た項目だけをFableがブラインド裁定する(§5)。これで『警告したもののうち本当に問題があった割合』(P-a)を**実際の有病率で直接**測れる(RecallはP-aでは測らない)。ラベル付きセットは、Recall・重大誤訳の検出・方式間比較に使う。
判定は P-a を主、P-b/P-cを副とする案(Fableが確定)。P-aの分母が小さいと区間が広い点は区間つきで正直に報告する。

## 3. 判定規則(事前登録・途中緩和禁止)
1. **目標**: Precision 80〜90%(ユーザー目標。保証でない)。**達成の判定=held-out(ラベル付き)およびプールで、凍結した方式のPrecision点推定>=80%**。区間の下限が80%未満の場合は『点推定は達したが区間は下限未満』と併記し、合格を断定しない。
2. **重大誤訳の見逃し抑制ガード**(極端に絞った高Precisionを排除): 採用候補の規則・方式は、dev・held-outとも severity=major の問題項目の検出率>=85% を満たすこと。満たさない場合は『見逃しが大きい』として不採用(Precisionがいくら高くても)。数値(85%)はFableが確認して事前登録を確定する(本計画の提案値)。
3. **規則**: 警告化規則は R_strict / R_default / R_loose の3つのみ(DESIGN_OPTIONS_01 §3)。devで1つ選んで凍結。held-outを見てから規則を選び直すことは禁止。
4. **未達の扱い**: 基準未達なら未達として報告(ユーザー原文§4)。『部分的に有効』『運用でカバー』等の言い換えで合格扱いにしない。Statusは基準に従い VALIDATED / REJECTED / USER_DECISION_REQUIRED を選ぶ(ユーザー原文§7)。
5. **早期終了**: (a)devで全方式のPrecision(P-b)が60%未満なら、以降の反復を打ち切り現状と代替案を報告。(b)held-outで目標を達したら追加Trialをしない。
6. 方式の追加費用が採用の妥当性に与える評価(ユーザー原文§6): 追加費用/セットと『確認負担の削減・発見できる誤訳数』を並べて報告(¥70に対する比率も)。許容額の閾値はユーザー未指定のため、本計画では設けず、数値で提示してFable/ユーザーが判断する(参考: DESIGN_OPTIONS_01 §2で全方式が¥1/セット未満)。

## 5. Fable裁定の手順(ラベル保留T4と、警告が出た『正常』項目)
1. **T4の事前裁定**(held-out評価の前に実施): 14項目を、警告情報を一切見せず、(表現・現訳・該当英文・前後文・記事全文・level)だけ見て problem / normal / exclude をFableが決める。記録=`eval_set/fable_rulings_T4.json`。裁定前はT4をPrecision/Recallに含めない。
2. **警告が出たT2・プール項目の事後ブラインド裁定**: 警告が出た項目(T2とプール)と、警告が出なかった項目をランダムに混ぜ、モデル出力(警告・理由)を隠したシートで『この訳は本文の文脈で問題か』をFableが判定する(警告の有無を知らない状態)。裁定でproblemになったT2はラベルを更新(更新履歴を残す)。**閾値・Promptの調整には使わない**(held-outの裁定結果をdevに戻さない)。
3. Fableの裁定が割れる/確信が持てない項目は、ユーザー確認の対象にせず `exclude` とし、除外件数を報告する(重要判断ではない)。除外が多い場合のみ判断候補にする。
