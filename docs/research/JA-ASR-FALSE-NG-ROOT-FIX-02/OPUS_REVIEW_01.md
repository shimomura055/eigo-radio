# OPUS独立技術レビュー: JA-ASR-FALSE-NG-ROOT-FIX-02 案R(条件A、read-only、API 0)

## 総合判定: 条件付きGO

GOの範囲は「(i)をコアにしたPhase 2のproto/Trial」と「(ii)の実測」です。
次の3点は現案のままでは進めないでください。
- (ii)を「best-of-N(どれか1本PASSなら合格)」のまま設計すること。NO-GOです。集約規則を変えてください(M-3)。
- (v-c)を「読み候補辞書に『超→こえ』を足す」形で実装すること。NO-GOです。既存方針と衝突します(M-5)。
- (iv)を新しい「条件付きPASS」状態として作ること。不要です。既存のHR Lock/人間承認で足ります(R-4)。

正直な見通し(論点7): 安全条件を守ると、機械判定で到達できるのは**6本中4本(PASS_W)**です。残る2本(ms_03 a1・reselect a3)は、安全条件を保ったままでは**機械的にPASSにできません**。この2本は「緩めない限りPASSにならない」型です。(ii)と(v-c)を重ねて通すと、ユーザー禁止事項「安全基準を緩めて6本を通す」に実質的に該当します(根拠はM-3・M-5)。

## 必須(M)

**M-1 Primary側の不規則読みガード(論点1)**
- 現状: v2のVALUE_ONLY経路は、不規則読みガードをSecondary側にしか持っていません(`proto_reading_compare_02.py:132-136`、`side == "secondary"`の条件)。このため『一日中→ついたち中』がPASS_Wになります(EVAL_UNIFIED_01.md:217-219)。
- 設計要件:
  - (a) 判定するsideに関係なく適用する。βの`_core`と同じく、原稿atomに`is_irregular_sig`が1つでもあれば新層は不適用にします(`b_light_proto_02.py:217-219`と同形)。
  - (b) ブロックした場合はNGにせず、**M0(Production)の判定結果をそのまま返す**。M1⊇M0を構造で保証します。
  - (c) PRON経路にも同じガードを入れる。現状はVALUE_ONLYにしか効いていません。
  - (d) testで固定する: `is_irregular_sig`の対象集合(一日・二日・二十日・二十歳・一人・二人など)を列挙し、正例×負例の両方で確認します。M0の基準線PASS_W(『三人で一日に会った』型、EVAL:231)が変わらないことも確認します。

**M-2 「常にPASS_W」を実装で保証する(論点1・4)**
- 理由: unified judgeは、warningsが空ならclean PASSを返します(`er078_asr_unified_judge_01.py:561-562`)。v2のVALUE_ONLY経路はwarningsを`g.warnings`しか持たず(`proto_reading_compare_02.py:128,138`)、clean PASSになりえます。Productionの既存値等価層もstate=PASSです(`er078_asr_unified_ja_wiring_test_01.py:163`)。
- 要件:
  - 新層の救済(PRON・β composite・再試行救済・読み変種)は、必ず専用のwarning codeを`warning_labels`へ載せる。
  - 新ラベルを`APPROVED_EQUIVALENCE_BASES`(`er078_asr_unified_judge_01.py:73-77`)に入れない。最終ANDゲートを必ず通すためです。
  - 両方をtestで固定する。
  - 既存`_numeric_value_equivalence`の受理範囲を超えるVALUE_ONLY救済にもwarningを付ける。
- 試聴リストには新方式救済のwarning_typeを別に立て、集計もPASS/既存PASS_W/新方式PASS_Wの3つに分けます(ユーザー§6「同一視しない」への対応)。

**M-3 (ii)ASR再試行は「best-of-N」ではなく「矛盾なし合意」で集約する(論点2)**
- 廃止理由との関係:
  - 承認済み仕様で同一音声の再転写(Primary#2)を廃止した根拠は「転写同一で独立性なし/日本語HR 8件は全て同一転写」でした(`er058_output/design/UNIFIED_FLOW_SPEC_V04.md:225` C-9、DESIGN_01 §4-9 `er058_output/unified_all_roles_production_wiring_01/DESIGN_01.md:339`、`CURRENT_SPEC.md:2926`)。
  - 今回の実測は、再ASR12本中10本が異なる転写です(RESIDUAL:27)。**仕様の前提事実が変わった**ことになり、再検討の正当な理由になります。ただし、変えるには承認済み仕様の変更としてユーザー判断が要ります(D-1)。
  - 廃止理由は「独立性なし・費用」であり、釣り(誤PASS)対策が理由ではありませんでした。釣り対策の上限設計は今回新しく必要になります。
- 釣りの実例(本データ内): (ii)が6本に新たに足す効果は**reselect a3の1本だけ**です。そのPASSは、OpenAI 5drawのうち1本だけ(『月野市は、八千九百本超』)がv2 Primary単独でPASSした結果です。他の証拠は逆方向で、OpenAI 2本とAzure 1本が『スギノ/Sukino』です(EVAL:130-134)。さらにPrimary PASSはSecondaryを呼ばずに確定します(`er078_asr_unified_judge_01.py:632-633`)。つまり、**多数派の反証を捨てて少数派のdrawを採る**ことになり、これは最も危険な型です。
- 要件:
  - (a) 再試行で救済したPASSは`force_secondary`を必須にする。
  - (b) N本すべてのdrawとSecondaryを保存し、**内容span(値以外)で原稿と食い違うdrawが1本でもあればPASSにせずHRへ回す**。説明できる例外は、βの`explain_garble`で説明できる数値garbleと、M-1・C2を通過したPRON同音だけです。
  - (c) 再試行救済は必ずPASS_W。
  - (d) Nは3本以下(追加2回まで)。
  - (e) 発火する理由はホワイトリストで限定する(例: `p1_value_diff`/`secondary_not_accepted`のうち、否定差・A7・C2・length以外)。
  - (f) Azureは再試行しない。実測で決定論的でした(RESIDUAL:38、3/3一致)。設計案の「必要ならAzure」は削ってください。
  - (g) OpenAI転写にcacheを入れる場合、cache keyがdrawを潰さないようにする(SecondaryCache型のsha単位keyでは再試行が無効になります)。
  - (h) 各drawをCOST_GUARD($0.05/segment)と累積ASR上限60へ計上する(DESIGN_01:307,346)。
  - この規則にすると、reselect a3はHR行きになり、**(ii)が6本に足す効果は0本**です。(ii)の価値は「一般的なdrawノイズによる再生成の削減」だけになるので、その価値をPhase 2で実測してから判断してください。

**M-4 βの「Secondary読み食い違い=warn」を再試行と組み合わせない(論点1・2)**
- β既定の`secondary_reading_conflict="warn"`(`b_light_proto_02.py:258-264,277`)では、ms_03 a3でAzureが『杉野氏』でもPASS_Wになります。drawが1本なら「Primary1本対Azure」の対立としてPASS_W+試聴で許容できます。しかし再試行と組み合わせると、**PrimaryのdrawをAzureと食い違わないものが出るまで引き直す**経路になります。
- 要件: 再試行が発火したsegmentではvetoとしてHRへ回す。または、β救済と再試行救済を同じsegmentで併用しない。

**M-5 (v-c)『超→こえ』を辞書の保守として扱わない(論点3)**
- `reading_candidates_for_span`はpykakasi同梱のkanwadictを読むだけです。冒頭に「個別漢字ごとのハードコード表(1対1 whitelist)は主方式にしない方針(CURRENT_SPEC既存の禁止事項)」と書かれています(`er008_asr_variant_hardening_15_ja_kanji_readings.py:13-18,63-83`)。『超』に『こえ』を足すのは、この方針に反する**新しい受理面**です。
- 副作用: 候補が2つ以上になると、C2逆方向ブロックの対象が増えます(`proto_reading_compare_02.py:84-87`)。その結果、ASRが『超』と書く既存PASSが新たにNGになる回帰が起きえます。
- 『超』を『こえ』と読むのは、標準読み(ちょう)と違う「**意味等価な非標準読み**」です。この種の読みを一般に受け入れるかは品質基準の判断です(D-2)。今回ユーザーが試聴OKとしたのは1本単位の判断で、規則化の承認ではありません。
- 進めるなら、汎用辞書を変えずに別表を作ります。「送り仮名省略形の訓読み」として、新層の中だけで参照します。条件は次のとおりです。
  - 両エンジンが**読みの水準で**一致すること。OpenAI『超え』とAzure『越え』は表記が違うので、表記一致では足りません。
  - 置換した後の残り差分が0文字であること。`_numeric_value_equivalence`と同じ厳格さで、E4型の便乗を防ぎます。
  - C2候補spanを除外すること。
  - 必ずPASS_Wにすること。
- ms_03 a1を通すには、(v-c)に加えて(ii)の再試行も要ります(stored drawの『8000句800』は`explain_garble`の対象外で、βでは救えません)。**緩和を2つ重ねないと通らない**こと自体が、この1本はHRに回すべき対象だという証拠です。

**M-6 E3/E4との干渉は実測ではなく構造で防ぐ(論点5)**
- 「1706行で回帰0」は経験的な結果で、将来の入力を保証しません。
- 要件:
  - `candidate_e_rejections`(E3)が空でなければ、新層(v2/β/v-c)は不適用にする。`er007_ja_secondary_asr_01.py:575`で取得済みです。
  - E4の`candidate_e_cascade_diffs`がある場合は、新層がそのdiffを救済根拠にしていないことをauditで確認する(`:577`)。
- testで固定してください(OPUS_REVIEW_01_OPEN333 R-6と同じ多層防御の考え方)。

**M-7 βの証人としての独立性を前提として固定する(論点1)**
- βの安全性は、JAのAzureがPhrase Listなし(DESIGN_01:305)で、原稿値を知らないことに依存しています。
- 要件: `composite_judge`の入口で`phrase_list_hash`が空であること(原稿テキストをAzureへ渡していないこと)を確認し、満たさなければfail-closedにする。将来JAへPhrase Listを足すと、「Secondary=原稿」の最悪ケースが日常的に起きるためです。

- **R-2** v2の`ENGINE_reading_difference`経路(助詞も値も関係しない読み一致、`:153-154`)は、本コーパスでは発火0です。Production化の範囲から外してください(必要性が実証されていないため)。

- **R-6** 要約表(DESIGN_PROPOSAL §2・§3)の「(ii)併用で5/6」は、M-3の安全条件の下では「4/6+HR 2」になります。ユーザーへ出す前に表記を直してください。
- **R-7** Store再利用とresume: 再試行を使ったentryには、全drawの転写・集約規則の版・新層の版を保存してください。`rejudge_with_current_judge`はAPIを呼び直さず、保存したdraw集合だけで再現することをtestで固定します。flag OFF・scope外のblockを先に行う点は、`composite_reuse_decision`(`b_light_proto_02.py:316`、BLIGHT M-2)と同形にします。

## Phase 2実測設計への具体的要求

1. **事前登録**: 集約規則はM-3の「矛盾なし合意」を主とし、参考として「best-of-N」も評価します。あわせて、N(2・3)、発火の理由ホワイトリスト、指標、合否基準を、draw取得の**前**にファイルへ固定してください。同じデータで規則を調整して、その結果を成果として報告することは禁止です。
2. **負例の母集団を広げる**: N3の30wavのうちM0でNGのものは約16本です。4drawでも、誤PASS 0/16の場合の95%上限は約17%で、大きな増加しか否定できません。保存済みの**人間がNG判定した実誤読wav**(HR queue由来など)を全件加えてください。1drawあたり¥0.0056なので、200wav×4drawでも約¥5で、承認済みScope内の自律範囲です。Q＞Cの観点から、¥1上限にこだわる理由は弱いです。
3. **正例側も測る**: 6本に加え、Y/Preview 4本、既存のHR承認済み誤NG wavを入れ、効果(救済率)を測ってください。
4. **drawの独立性**: wav別の分布を報告してください(ms_03 a2は再転写3本が同一でした)。N=2・3の効果は、4drawの全部分集合から計算し、出した順に依存させないでください。
5. **再現性の記録**: モデルID、応答メタデータ、時刻、draw順を保存し、変動が時刻(モデル更新)によるのかdraw単位なのかを分けてください。
6. **(v-c)を評価する場合**: 回帰(既存PASS→NG)を全1706行+Secondary保存転写で測ってください(C2の候補数変化の影響)。
7. **M-1・M-6・R-1のガードを入れた版で**、EVAL §3の増分表を作り直してください。

## ユーザー判断が必要な点(判断はFable/ユーザー)

- **D-1** (ii)の採用: 承認済み仕様「同一音声のOpenAI再転写は廃止」(`CURRENT_SPEC.md:2926`)の変更です。根拠となった前提(独立性なし)が実測で覆ったことを示し、M-3の安全条件付きで判断を求めることになります。ただし6本への効果は0本の見込みです(M-3)。
- **D-2** 「意味等価だが非標準のTTS読み」(超→こえ)を一般に受理するか: 品質基準の判断です。代わりに(v-a)のTTS入力側の読み固定(Production TTS挙動の変更)で、発生源を防ぐ選択肢もあります。
- **D-3** 新方式で救済したPASS_Wを、既存PASS_Wと同じく**非ブロッキングの事後試聴**にするか(`CURRENT_SPEC.md:2927`)、**公開前の試聴を必須(ブロッキング)**にするか。ユーザー§6「同一視しない」の解釈次第で、M-2の集計分離だけで足りるかどうかが変わります。
- **D-4** 合格条件1「6音声すべて最終判定でPASS」への対応: 安全条件の下では、機械判定で4/6(PASS_W)+人間承認2/6が上限です。人間承認(HUMAN_APPROVED)を最終判定として数えるか、この限界を受け入れるかを判断してもらう必要があります。限界を隠して緩和を重ねるのは不誠実です(論点7)。
