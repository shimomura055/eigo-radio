- 目的: Fact Lock の性能を測る Trial で、【事実N】・重要数値(中核/周辺)の注記が人の都度判断で記事ごとに揺れるのを防ぐ。注記を機械的に再現できる規則として固定する(ユーザー決定 2026-10-09 B3)。
- 適用: 旧4(META・ホルムズ・宇宙兵器・ミニバッグ)+新6(ユーザー選定の新テーマ)の**全10記事に同一の本仕様を適用**する。**過去の注記版(`briefs/*/b2/selected_brief_factlock.md`、`astra_revise_matrix_02/inputs/small_bag/selected_brief_factlock.md`)は使わず、旧4も再注記する**。
- 確認済み: 過去の注記は `factlock_writer_trial_01/tools/annotate_briefs.py` の SPEC 辞書による人手指定で、規則文書はなく(DESIGN_01.md に「中核は記事あたり最大3、選定は実装者の手付け」とのみ記載)、ミニバッグは Selected Facts の3事実化・数値注記を人間が決めた(REPORT §108)。
- 範囲外: 注記の実施(本書は仕様のみ)、注記の自動化(§8)、Writer プロンプトの変更。

## §1 入力・出力の定義
入力(注記者が受け取るもの): (1) 元B3 brief(`selected_brief.md`、旧腕B3原本)、(2) 台帳 `verified_fact_ledger.txt`、(3) 本仕様(sha256固定版)。
出力(注記者が作るもの、記事ごとに3ファイル):
1. `selected_brief_factlock.md` — 注記版 brief。
2. `annotation.json`(サイドカー) — 下記スキーマ。**Writer には渡さない**(監査・照合専用)。
3. `core_numbers.json` — サイドカーから機械生成(`b3_annotation_check_01.py --emit-core-json`)。既存 harness の `load_core_numbers` と同形式(`core[].literals`、`peripheral[]`)。確認済み: harness はこの形式を読み、`max_core_per_article` を強制するコードは見当たらない(Grep確認)。
4. (er019 再利用分岐がある場合のみ)注記版 `fact_selection_evidence.json` — 元JSONの `selected_fact_brief_text` だけを同じ注記規則で置換したコピー。他のキーは**バイト同一**。

**絶対規則(追加のみ)**: `strip_tags(注記版) == 元brief原文`(行末空白のみ無視)。注記は 【事実N】【中核数値】【周辺数値】 の3種の印の**追加のみ**で、削除・言い換え・語順変更・句読点変更を禁止する。印の種類はこの3つだけ(他の【】は禁止)。
- 例外(レイアウト正規化L): 元briefの Selected Facts が箇条書きでなく段落の場合のみ、各【事実N】を箇条書き行頭に置くため行頭に `- ` と改行を挿入してよい。この場合サイドカーに `"layout_normalized": true` を必須記載し、検査は「行頭の箇条書き記号・空白・改行を除いた文字列の一致」で代替する(`PASS_LAYOUT_NORMALIZED`)。理由: 既存 harness の `FACT_LINE_RE`(`^\s*(-|・)\s*【事実N】`)が箇条書き行頭の印のみを読む(確認済み)。この例外は旧腕(段落のまま)と新腕(箇条書き化)でbriefの体裁だけが違う状態を生むため、§8 の限界に記録する。
- 判断記録: 旧4のうち段落形式なのはミニバッグのみ(確認済み)。

サイドカー `annotation.json` スキーマ:
```
{ "slug": str, "annotator": "A|B", "spec_sha256": str, "brief_sha256": str, "layout_normalized": bool,
  "facts":   [ {"n": 1, "ledger_ids": ["HF-002", ...], "note": ""} ],
  "numbers": [ {"surface": "20％", "class": "core|peripheral", "kind": "magnitude|date_time|range|year|ordinal|name_embedded",
                "concept": "C1", "ledger_id": "HF-002", "role": "提案率"} ],
  "unmapped_claims": [ "briefにあって台帳に無い記述" ],
  "annotation_notes": [ {"where": "...", "question": "...", "options": ["..."], "chosen": "...", "rule": "§5-x"} ] }
```
`concept` = 同じ台帳データを指す表記の束(例 `2026年9月14日` と `2026年9月` は同じ概念)。中核の上限・分類の一貫性は概念単位で数える。

## §2 【事実N】の分割規則
**単位の原則: 台帳fact ID の境界で分ける。** brief の Selected Facts の1項目(箇条書き1行、段落形式なら文の塊)を既定で1事実とし、次の条件のときだけ分ける。
- **分割条件(全て満たす)**: (S1) 項目内に2文以上ある。(S2) 異なる文が、台帳の**異なるfact ID**を主な根拠にしている(文Aの主張は台帳X、文Bの主張は台帳Y≠X)。→ 文の境界(`。`)で分ける。
- **分けない場合**: 同一文の内部(主体・行為・対象・時期・数量などの要素を理由に文を割らない)。1つの台帳factに載っている複数要素(例: 副社長が「ミス」と認め、かつロールバックした)。限定文(「これは〜を意味しない」「〜とは書かない」「Muse全体の停止ではない」)は直前の主張文と同じ事実に属する(別事実にしない)。
- **独立に誤りうる要素の扱い**: 要素ごとの分割はしない。代わりに、数量・日付は §3 の数値注記で個別に保護される。主体・範囲・時期などの定性要素は台帳の fact ID 単位の照合に任せる(これが Fact Lock の測定対象)。分けすぎると事実数が膨らみ、タグ照合の条件が記事ごとに変わる。
- **上限**: 1項目あたり最大3事実まで(4以上に分けたくなったら §5 の「分けない」を適用し、迷いとして記録)。記事あたりの事実総数の上限は設けない(台帳側で決まる)。
- **1台帳fact → 複数【事実N】**: briefが同じ台帳factを別項目で繰り返す場合は許す(各Nに同じ ledger_id)。**1【事実N】 → 複数台帳fact** は、1文が複数台帳factの内容を統合している場合のみ許す(ledger_ids に併記)。
- **非事実行**: `## Storyline` の文、Selected Facts 内の `Storyline：…` 重複行、`素材:` 行には【事実N】を付けない(数値印は §3 により付ける)。
- **番号付与の順序**: briefの出現順(上から下)に 1..K の連番。台帳IDの順序・数値の大小は無関係。欠番・重複・飛びは禁止。

## §3 重要数値の規則
前提: 本規則での「数値」= 算用数字(全角含む)を含む表記。漢数字だけの数量(三千人、二国間)は **v1の対象外**(§8)。検出された場合は `annotation_notes` に記録し、印は付けない。台帳ID(F-001、MUSE-HC-006、GPT-6 のような `英字-数字` 形式)は数値でも名称内番号でもなく**印を付けない**(harness の `ID_RE` と同じ扱い)。

### 3-1 数値表記(surface)の取り方
- 数字+単位+ヘッジ語を**一つの表記**とし、印は表記の末尾に付ける。例: `約2.6％【中核数値】`、`1バレル85ドル【中核数値】`、`1,500個超【中核数値】`。
- ヘッジ語は表記に含める: 前置 約・およそ・ほぼ・最大・最大で・少なくとも・数、後置 超・以上・以下・未満・前後・近く。含めない語: 文脈上の「一時」「当面」など数字に直接付かない語(`annotation_notes` に記録)。brief が「を上回って」のように数字の外でヘッジする場合も表記には含めず、注記しない。
- 範囲(`3〜5％`)は1表記(kind=range)。日付と時刻の連続(`7月13日午前10時16分`)は1表記。相対日付(`翌14日`)は数字部分(`14日`)を表記にする。
- 同一表記は記事内で**同じ分類**(全箇所に同じ印)。短い表記が長い表記の一部になる場合(`2026年9月` が `2026年9月14日` の中)は、長い方の表記に1回だけ印を付ける。

### 3-2 種別(kind)
| kind | 内容 | 中核になれるか |
|---|---|---|
| magnitude | 割合・金額・件数・個数・価格・倍率など量 | なれる |
| date_time | 年月日・年月・時刻・期間 | 条件付きでなれる(3-3 E2) |
| range | 範囲 | なれる |
| year | 年のみ(`2026年`) | **なれない**(常に周辺) |
| ordinal | 識別子としての序数(`第4条`、`第137回会合`) | **なれない**(常に周辺) |
| name_embedded | 名称の一部としての番号(`COSMOS 1408`、`Fall 2026`、`iPhone 17`) | **なれない**(常に周辺) |

**名称内番号の規則**: 「番号を変えると別のものを指す」ものは識別子(ordinal/name_embedded)で、数値扱いしない=中核にしない。印は【周辺数値】を付ける(印を付けない案Xではなく、既存 harness の数値検査との整合と、Fact Lock v1 で採用済みの案A「周辺のまま、数字を省いて名称を書く」の継続を優先。選択肢の比較は OPUS_POINTS 参照)。「番号を変えると量や日付が変わる」ものは数量(magnitude/date_time)。順位(`3位`)は主張の中身なので magnitude。

### 3-3 中核の判定(機械的に決まる適格性)
中核は次の**適格条件のどちらか**を満たす数値の概念に限る。
- **E1**: 紐付く台帳factの `numeric_value` 欄に、その数字がある(台帳が数量として宣言している)。
- **E2**: E1ではないが、(i) 台帳factの `date_or_period` 欄にその数字があり、かつ (ii) その表記(または同じ概念の短い表記)が `## Storyline` に出現する(記事の骨格で時期が主張されている)。
適格でない数値は常に周辺。適格な概念が複数ある場合は上限(3-4)まで次の優先順で中核にする: (1) E1でStorylineに出現、(2) E1でStorylineに無い、(3) E2、同順位はbrief出現順。台帳にその数字が無い数値(`ledger_id` を付けられない)は中核にできない(周辺にして `number_not_in_ledger` として記録)。

### 3-4 上限と「数字が記事の主役」の場合
- 数える単位: **概念**(同じ台帳データを指す表記の束)。名称内番号・年のみ・序数は数えない。
- 上限 = `max(3, min(6, floor(n / 2)))`、n = 数える概念の総数(magnitude・date_time・range)。n≤7 なら3、n=8〜9 なら4、n=10〜11 なら5、n≥12 なら6(これが主役型の記事の上限)。
- **全件を中核にすることは禁止**(上限は概念総数の半分を超えない)。上限を超えた適格概念は周辺にして、`annotation_notes` に「cap超過で周辺化」を記録。
- 閾値(`n//2`、上限6)はTrial前に固定する(§9)。根拠: 旧4の既存注記は全て上限3以内(確認済み)で、主役型記事(価格高騰・統計)は旧4に含まれないため、主役型の挙動は新6で初めて測られる(**未確認**)。

## §4 台帳由来制約
- 注記してよい情報は台帳(fact ID、statement、`conditions`、`scope`、`date_or_period`、`numeric_value`、`notes_for_writer`)に存在するものだけ。注記者が台帳外の知識で事実の根拠や数値の正しさを補わない。
- **brief にあって台帳に無い主張**: 注記しない(そのまま残す)。`unmapped_claims` に列挙する。**肯定的な主張**(新しい事実・数値・因果)が台帳に無い場合は、その記事の注記を**STOP**して Fable に報告する(B3が台帳外の事実を混入させた=上流の欠陥であり、注記で隠さない)。**限定・否定文**(「〜と断定しない」など制限するだけの文)は台帳の `notes_for_writer` 等に根拠が無くても残してよいが、`unmapped_claims` に記録する。
- **台帳IDを注記に併記しない**(Writerへの入力は `【事実N】` のみ。Writerのプロンプトと出力形式を過去Trialと同一に保つため)。照合用は**サイドカー** `annotation.json` の `facts[].ledger_ids` に保存する。briefに元から台帳ID(`F-001：`など)が明示されている場合はそのまま残し、サイドカーの `ledger_ids` と一致させる。
- 数値の表記は brief の表記を使う(台帳の表記に直さない。直すと strip 後の原文一致が崩れる)。台帳の表記と違う場合(`約2.6％` と台帳の `約 +2.6%`)はサイドカー検査が `surface_diff` として記録する(失敗ではない)。

## §5 迷った場合の規則(決定木)
迷いは必ず `annotation_notes` に `{where, question, options, chosen, rule}` で記録する。判断は次の既定に従い、**人の主観で上書きしない**。
1. 分けるか分けないか迷う → **分けない**(§2のS1・S2を機械的に判定。判定不能なら分けない)。
2. 中核か周辺か迷う → **周辺**(3-3の適格条件を満たすことを台帳で確認できない限り周辺)。
3. 数量か名称内番号か迷う → **名称内番号**(中核不可側)。
4. 紐付く台帳factが複数候補で決められない → 該当する台帳IDを**全て**ledger_idsに列挙(1つに絞らない)。それでも根拠が見つからない → §4のSTOP判定。
5. ヘッジ語を表記に含めるか迷う → 含める(数字に直接隣接する語のみ)。
6. 上限を超える適格概念の選び方 → 3-3の優先順、同順位はbrief出現順。
7. 漢数字の数量表現 → 印は付けず記録のみ。
8. 規則に該当しない状況 → 記録して**既定=注記しない**側(追加の印を付けない)。ただしその記事の注記全体が規則で決まらないと判断される場合はSTOP。
迷いが3件を超えた記事は、検証時に「規則の曖昧さ」の候補として集計する(仕様改訂はしない=§9)。

## §6 照合・検証手順
検証は `b3_annotation_check_01.py`(¥0・LLM不使用)で行い、結果JSONを証跡として保存する。
- **(a) 原文一致**: `strip_tags(注記版md) == 元md`(行末空白のみ無視)。JSONがある場合は `strip_tags(注記版JSONの selected_fact_brief_text) == 元JSONの同キー`、かつ他キーが元JSONと同一。sha256を記録。レイアウト正規化(§1例外L)は宣言がある場合のみ代替判定を許す。
- **(b) 台帳紐付け**: 全【事実N】がサイドカーの `ledger_ids` ≥1件に紐付き、台帳に存在する。briefに明示された台帳IDとサイドカーが一致。
- **(c) 数値**: 数字が全て(宣言された表記 or 台帳IDパターン)に覆われる(分類漏れ=0)。印がサイドカーの分類と一致(欠落・誤分類・孤立印=0)。中核は台帳の `ledger_id` に数字が存在し、E1/E2適格、種別が中核可、概念数が上限以内、概念内の分類が一貫。周辺で台帳に数字が無いものは警告。surface差は記録。
- **(d) 連番**: 【事実N】が箇条書き行頭のみに 1..K で連番、重複・欠番なし、未知の【】印なし。
- **(e) 二重注記プロトコル**: 注記者A・Bは**別worker・別context**で独立に注記する。入力は §1 の3点のみ。注記者には生成結果・腕の割当・採点・過去の注記版を**見せない**。双方のサイドカーと注記版を保存。
  - 一致率: **分割一致率** = 元の項目(箇条書き1行/段落の文塊)のうち、分割(事実境界とledger_ids集合)がA・Bで一致した割合。**中核数値指定一致率** = 中核概念集合のJaccard(A∩B / A∪B、両方空なら1.0でn=0と明記)。**分類一致率** = 数値表記の和集合のうち class が一致した割合。いずれも記事ごと+全体で記録。
  - 不一致の**機械的解決**(人が裁定しない): 分割不一致 → 事実数の少ない(粗い)方を採用(ただし両者のledger_ids全てを保持)。中核不一致(片方のみ中核) → 周辺。種別不一致 → 中核不可側(name_embedded > ordinal > year > range/date_time > magnitude の順で優先)。ledger_ids不一致 → 共通部分(空なら**STOP**してFableへ)。印の位置ずれ → 短い方でなく長い表記に統一。解決後の版を最終版とし、解決内容を `resolution_log.json` に記録(どの規則を適用したか)。
  - 解決後の最終版に対して(a)〜(d)を再実行する。FAILなら最終版を採用せずSTOP。
  - 層別報告: 旧4は過去に注記を見た経験のあるworkerかどうか、新6は注記者(Sonnet)で別層として報告する。**推奨**: 全10記事を新規worker 2名(A・B)に注記させ、旧4で過去注記者が混ざる場合は「汚染層」として分けて報告する(Fable判断、OPUS_POINTS 論点6)。
- **(f) 注記者が参照してよいもの**: 本仕様、元brief、台帳、検証スクリプト(自分の出力の自己検査)。**いけないもの**: 過去の注記版・`ANNOTATION_LOG.md`・`core_numbers.json`、各腕の生成記事・RESULT/REPORT・採点、腕の割当、もう一方の注記者の出力、web検索(台帳外の確認は不可)。

## §8 既知の限界
1. **人手注記の上限性能**: 本Trialは固定規則を人(AI worker)が適用した結果で、Production化にはB3自身が同等の注記を自動で付ける必要がある。B3の自動注記の精度は未測定(**未確認**)。二重注記の一致率が低い場合、規則が機械適用できていないことを示す。
2. Luna Fact Check(FC)が「不在・未成立」型(「〜はない」「〜しなかった」型の断定)を取り逃す件(`RESIDUAL_NG_VS_CHECK.md`のタグ検査で拾えなかったNG)は、**本仕様の注記では防げない**。注記は台帳にある事実の範囲を明示するだけで、台帳が沈黙している点をWriterが断定で埋める誤りは別の検査の領域。本仕様は「何を注記したか」を揃えるものであり、この限界の改善を主張しない。
3. 漢数字・ひらがな数詞・「倍」「半分」「数年」などの数量語は対象外(既知。`DESIGN_01.md` §3-1 と同じ)。
4. E1/E2は台帳の欄名(`numeric_value`・`date_or_period`)に依存する。新6の台帳が同じ欄を出力するかは**未確認**(旧4のうちミニバッグの台帳は `numeric_value` を持たない=確認済み)。欄が無い台帳では日付型の中核が出にくい。
5. harness は `max_core_per_article` を強制しないが、Writerプロンプトが「中核は最大3」と書いているかは**未確認**(上限4〜6の記事で挙動が変わる可能性)。
6. レイアウト正規化L(段落→箇条書き)は旧腕と新腕でbrief体裁が違う状態を作る(ミニバッグのみ)。
7. 台帳IDをWriterに見せない設計のため、Writerが台帳IDを参照できる利点は測らない。
8. 旧4の過去注記者が再注記すると、過去の注記を覚えている可能性がある(§6(e)層別で対処)。
9. 現行runnerが再利用分岐で md と JSON のどちらを読むかは**未確認**。JSON本文は md と異なる文面になりうる(確認済み: all6 hormuz の `fact_selection_evidence.json` の `selected_fact_brief_text` は md と文面が異なる)。そのため JSON は md から機械変換せず、JSON本文自体に同じ規則で注記して別途 (a) を検査する。

## §9 変更禁止事項
- 本仕様(sha256を事前登録に記録)・検証スクリプト・上限式・適格条件(E1/E2)・既定(§5)・解決規則(§6(e))は、Trial開始後に変更しない。
- 変更が必要になった場合: 注記を停止(STOP)し、変更案と理由を記録してFable/ユーザーへ報告する。変更した場合は仕様 v2 として**全10記事を再注記し、結果をv1と混ぜない**。
- 注記後に注記版を手で直さない(検証FAIL時は注記者の再実行ではなくSTOP。注記者は1記事につき A・B 各1回のみ)。
- 注記者・日時・使用モデル・入力sha256・出力sha256を全記事で記録する。
- 注記版・サイドカー・core_numbers.json は生成開始前にsha256を固定して保存し、生成後は編集しない。
