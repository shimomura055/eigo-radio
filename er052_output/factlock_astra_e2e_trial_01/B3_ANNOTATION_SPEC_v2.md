## §D 二重注記と統合(Opus点2・5)
- 注記者A・Bは別worker・別contextで独立に注記。双方の注記版とサイドカーを保存。それぞれ `b3_annotation_check_01.py` が単独でPASSであること(FAILならその注記者の出力は不採用でSTOP。手で直さない)。
- 統合は `b3_annotation_merge_01.py`(決定論・手作業禁止)。
  - 分割の食い違い -> 事実数の少ない(粗い)方 = 両者の境界の共通部分。事実の `ledger_ids` は、統合した各事実について A側の和集合 と B側の和集合 の共通部分(空ならSTOP)。
  - 数値表記は和集合。種類の食い違い -> 中核不可側(name_embedded > ordinal > year > range/date_time > magnitude)。台帳IDの食い違い -> 共通部分(空ならSTOP)。概念は A・B のラベルと、包含・同一主数字の規則で連結成分に統合。
  - **中核/周辺は A・B の宣言を使わず、統合入力から再計算**。位置ずれ(長い表記と短い表記)は最長一致で長い表記に統一。
  - 統合後に検査を再実行。FAILなら統合版を採用せずSTOP。`resolution_log.json` に適用した規則を全て記録。
- 一致率(`agreement.json`): 分割一致率 = 元の項目のうち分割(境界と ledger_ids)が A・B で一致した割合。中核Jaccard = 中核概念集合の |A∩B|/|A∪B|(概念は統合後の連結成分で同一視)。分類一致率 = 数値表記の和集合のうち class が一致した割合。記事ごと+全体で記録。数値0件の記事(中核の和集合が空)は Jaccard=1.0 に含めず、集計から除いて件数を併記する。
- **判定線(事前登録、推定値)**: 分割一致率 < 0.8、または 中核Jaccard < 0.67 の記事は「規則を機械的に適用できていない」と報告する(仕様の問題か注記者の問題かの切り分けは、食い違いの `resolution_log` と `annotation_notes` の迷い記録で行う)。判定線は事前に置いた推定値であり、根拠となる実測はない(**未確認**)。
- 層別: 旧4と新6は別に報告する。
- 解決規則は常に「粗い方・周辺側・中核不可側」へ寄るため、統合版の事実数と中核数は系統的に小さい側へ偏る(Fact Lock の照合範囲が狭く出る方向。方向を固定した偏りであり、両腕に同じ注記版を渡すため腕間比較には影響しない)。

## §E 検査(`b3_annotation_check_01.py`、¥0・LLM不使用)
- (a) 原文一致: 注記版から【事実N】【中核数値】【周辺数値】と、**定義済みの挿入(`。` 直後の `\n- `、節先頭行または `。\n` 直後の `- `。直後は必ず【事実N】)**だけを逆に除いた結果が原文と厳密一致。`COSMOS 1408` -> `COSMOS1408` のような空白の改変も検出する。JSONがある場合は同様に検査し、他キーは元JSONと同一。
- (b) 台帳紐付け: 全【事実N】が台帳に存在する `VERIFIED` の記録に ≥1 件紐付く。briefに明示された台帳IDとサイドカーが一致。
- (c) 数値: 数字が全て宣言された表記(または台帳ID形)に覆われる(分類漏れ0)。**宣言された表記が本文に1回も出ない場合はFAIL(架空の宣言)**。印がサイドカーの分類と一致。概念の束ね不備(概念内で台帳IDが共通でない、kindが割れている、別概念なのに短い表記が長い表記に含まれ台帳IDが共通、別概念なのに台帳ID共通で主数字が同じ)をFAIL。サイドカー宣言の class を `compute_expected` の計算結果と比較し、不一致をFAIL(付け漏れ・上限超過・不適格な中核・種類による中核不可)。
  - 数字の正規化: 全角->半角、`04`->`4`、`4.00`->`4`、`1,500`->`1500`。
  - 適格(E1): 量/範囲の**主数字**(表記末尾の数字列、範囲は両端。`1バレル85ドル`->85)が、紐付く台帳の `numeric_value` 欄の数字に含まれる。`(numeric_scope: …)` は除外してから照合。交差(1数字共通で可)は廃止。
  - 適格(E2'): 日付表記に月があり、紐付く台帳の `date_or_period` の**先頭の日付表現**(和文 `2026年9月14日`、ISO `2026-07-13 10:16 EDT`、`2026-06` など)と、表記にある年・月・日(・時刻)が全て一致。年のみ・日のみの表記は対象外。Storylineに出るかは条件にしない。
  - 代替規則(事前登録): 台帳全体に `numeric_value` 欄が1件も無い場合のみ、量のE1を `statement` 内の主数字で判定。台帳全体に `date_or_period` 欄が1件も無い場合のみ、日付のE2'を `statement` 内の先頭の日付表現で判定(欄が一部の記録にだけ無い場合は代替せず不適格)。欄名が違う台帳でも全数値が黙って周辺にならないようにするための規則。適用の有無は `f_ledger_schema` に出力。
  - 台帳スキーマ点検(`f_ledger_schema`): 各記録の欄の有無、欄名ごとの件数、`numeric_value` が無いのに `statement` に量を示す語(％・ドル・円・個・台・人・件・倍・km・基・社・万・億・バレル・賛成・反対・棄権・ポイント・位)がある記録の警告、`VERIFIED` でない記録の警告。
  - 警告のみ(持ち越し): 漢数字の数量、`%` と `％` の混在(NFKC差)。
  - 上限で外れた適格概念は `cap_dropped_concepts` / `cap_dropped_count` で**記事ごとに必ず報告**。
- (d) 連番: 【事実N】が箇条書き行頭(`- ` 直後)のみに 1..K で連番、重複・欠番なし、**複合タグ(`【事実1,事実2】`)禁止**、未知の【】印なし、Storyline/素材 行に【事実N】なし。
- (e) サイドカー照合: `spec_sha256`(注記者用仕様の実ファイル)、`brief_sha256`(元briefの実ファイル)、`annotator`(A/B/MERGED)。`unmapped_claims` は種類別(`new_fact`/`new_number`/`new_causal`/`generalization`/`specification`/`qualifier`)。
- 確認済み: 本スクリプト群は単体テスト(`b3_annotation_check_01_test.py`)で検証。実行結果は `RESULT` 節(委任_04 result)。
- 記録のみ(harness変更禁止): 既存 harness の `load_core_numbers` は中核の表記を NFKC 後に(値, 単位)へ分解する(`2026年9月14日` -> 2026年・9月・14日)ため、同じ(値, 単位)を持つ周辺数値(`2026年10月` の `2026年` など)が検査上「中核」と同一視されうる(周辺数値の取りこぼし)。本Trialでは変更しない。

## §F E2'の設計選択と旧4実測(Opus点4)
- **E2'は設計選択であり、ユーザー提示用要約では「推奨」と明記する**。v1のE2(Storyline出現を条件)は、日付の取り違えの保護を広げる代わりに旧4の過去注記と食い違った(宇宙・ミニバッグ)。E2'は台帳の欄だけで決まり、旧4の過去の人手注記と一致する見込みとなり、`b3_old4_expected_eval_01.py` で実測した(結果は `OLD4_EXPECTED` と result.md)。
- 実測の範囲と限界: 数値の表記・種類・概念・台帳IDは旧4について表で固定し(注記者の入力に相当)、事実分割は文の bigram 重なりによる近似ヒューリスティック(S1/S2の厳密な適用ではない)。中核/周辺は計算。したがって「規則の適用結果の目安」であり、注記者の実際の判断一致を示すものではない。

## §G 上限式とWriterプロンプト(Opus点6)
- 上限 = `max(3, min(6, floor(n / 2)))`、n = 数える概念(magnitude・date_time・range)の総数。n≦7 なら3、8〜9 なら4、10〜11 なら5、n≥12 なら6。式は固定。**n≦5 では適格概念が全て中核になりうる**(例: 宇宙兵器 n=3、ミニバッグ n=2)。優先順は Storylineにある量 -> その他の量 -> 日付、同順位は出現順。
- 閾値(`floor(n/2)`、上限6)の根拠は弱く、旧4は全て n≦7(上限3)で、主役型記事(価格高騰・統計)の挙動は**新6で初めて検証される**(**未確認**)。
- 確認済み: 現行 Writer プロンプト(`er052_factlock_writer_trial_01_run.py` L72-79、`FACTLOCK_R0_BLOCK` の規則5)は「【中核数値】と印の付いた数字だけを使える」とのみ書き、中核の最大数は書かない。したがって中核が4〜6件になっても Writer プロンプトとの不整合は生じない(影響なし)。harness も `max_core_per_article` を強制するコードは見当たらない。
- 上限で外れた適格概念は周辺になり、Writerはその数字を使えない(数字を省いて書く)。外れた概念数は記事ごとに報告し、解釈時の注意事項とする。

## §H STOP範囲と「B3由来」NGの別集計(Opus点7)
- 台帳外の記述(新事実・新数値・新因果・一般化・具体化・限定)は印を付けず、`unmapped_claims` に種類別で記録する。**注記はSTOPしない**。
- STOPは次の2場合のみ: (i) Storylineの主張そのもの(記事の骨格)が台帳に無い。(ii) 台帳に無い数字が、E1/E2'に適格な形(量または日付)で記事の中心(Storyline)にある。後者はスクリプトが `stop_candidates` として検出する(台帳に無い数字がStorylineに出る場合)。
- 評価時: `unmapped_claims` に記録された文に由来するNGは「B3由来」として両腕で別集計し、**Fact Lock 起因に数えない**。この扱いは `PREREGISTRATION_01.md` に事前登録事項として追加した。

## §I 既知の限界
1. **注記者A・Bが同モデル**で誤りが相関し、一致率が高めに出る。一致率が高いことは規則が機械的に適用できることの証明にならない。低い場合は規則が機械適用できていない強い兆候。
2. **人手(AI worker)注記の上限性能**: Production化にはB3自身が同等の注記を自動で付ける必要があり、その精度は未測定(**未確認**)。
3. Luna Fact Check(FC)の「不在・未成立」型(「〜はない」「〜しなかった」型の断定)の取り逃しは、本仕様の注記では防げない。
4. 漢数字・ひらがな数詞・「倍」「半分」「数年」などの数量語は対象外(持ち越し)。`%`/`％`のNFKC差は警告のみ(持ち越し)。
5. E1/E2'は台帳の欄名(`numeric_value`・`date_or_period`)に依存する。新6の台帳が同じ欄を出力するかは**未確認**(旧4のうちミニバッグの台帳は `numeric_value` を持たない=確認済み。代替規則を事前登録)。
6. レイアウト正規化(段落->箇条書き)は旧腕と新腕で体裁が違う状態を作る(ミニバッグのみ、旧4の中で段落形式)。
7. 台帳IDをWriterに見せない設計のため、Writerが台帳IDを参照できる利点は測らない。
8. 旧4の過去注記を覚えている可能性: 注記者は新規workerでありうるが、記憶の有無は検証できない。事後監査(§C)と層別で対処。
9. 現行runnerが再利用分岐で md と JSON のどちらを読むかは**未確認**。JSON本文はmdと異なる文面になりうる(確認済み: all6 hormuz の `fact_selection_evidence.json` の `selected_fact_brief_text` はmdと文面が異なる)。JSONはmdから機械変換せず、JSON本文自体に同じ規則で注記して別途(a)を検査する。
10. 名称内番号は案Y(【周辺数値】印)を継続(Fact Lock v1 の案A「数字を省いて名称を書く」と連続)。`COSMOS 1408` が「衛星」に省略される不自然さは残る。分割単位(台帳fact ID境界、主体・行為・時期で割らない、1項目最大3)は採用。

# 付録A 注記者用仕様(`B3_ANNOTATION_SPEC_v2_ANNOTATOR.md` の逐語収録)
# B3注記仕様(注記者用)

あなたの仕事は、ニュース記事の元になる「ニュース欄(brief)」に、事実番号と数字の印を機械的な規則で付け足すことです。与えられた台帳(裏付け済みの事実の一覧)に書かれていることだけを根拠にし、判断が分かれる場面は本書の既定に従います。自分の好みや読みやすさで上書きしません。

## 1 入力と出力
入力(依頼文に貼り付けられている3点だけ): (1) 元のニュース欄(brief)、(2) 台帳、(3) 本書。
出力: 依頼文で指定された形式で、(A) 注記版のニュース欄の全文、(B) サイドカー(JSON)、を返します。ファイルは作りません。

注記版の絶対規則: 元のニュース欄に、次の3種類の印と、定義済みの改行の挿入を**付け足すだけ**です。削除・言い換え・語順の変更・句読点の変更・空白の変更は禁止です。
- 印は `【事実N】` `【中核数値】` `【周辺数値】` の3つだけ。他の【】は使いません。
- 定義済みの改行の挿入は、「`## Selected Facts` 節の中で、文末の `。` の直後に改行と `- ` を入れる」ことと、「節の先頭の行(または `。` と改行の直後)の行頭に `- ` を入れる」ことだけです。どちらも直後に必ず `【事実N】` が続きます。

## 2 【事実N】の付け方
- 単位は、台帳の事実ID(例 ZZ-001)の境界です。ニュース欄の `## Selected Facts` 節の1項目(箇条書き1行、または段落の文のまとまり)を、既定で1つの事実とします。
- 次の2条件を両方満たすときだけ、文の境目(`。`)で分けます。(S1)項目の中に文が2つ以上ある。(S2)別々の文が、台帳の**別々の事実ID**を主な根拠にしている。
- 分けない場合: 同じ1文の中(主体・行為・対象・時期・数量などで1文を割らない)。1つの台帳の事実に載っている複数の要素。限定する文(「ただし〜」「これは〜を意味しない」「〜とは書かない」「〜ではない」など)は、直前の主張の文と同じ事実に入れます(別の事実にしません)。限定する文が別の台帳IDに由来する場合も、別事実にせず、その台帳IDを `ledger_ids` に追加します。
- 1項目で分けられる事実は最大3つです。4つ以上に分けたくなったら、分けない側を選び、迷いとして記録します。
- ニュース欄がすでに同じ台帳の事実を別の項目で繰り返している場合、それぞれに同じ台帳IDを付けて構いません。1つの文が複数の台帳の事実をまとめている場合は、`ledger_ids` に併記します。
- `## Storyline` の文、Selected Facts 節の中の `Storyline：` で始まる重複行、`素材:` で始まる行には、`【事実N】`を付けません(数字の印は後述の規則で付けます)。
- 番号は、ニュース欄の上から順に 1, 2, 3… と連番にします。欠番・重複・飛びは禁止です。`【事実1,事実2】` のような複合の印は禁止です。
- 台帳IDは注記版の本文に書き足しません(サイドカーに書きます)。ニュース欄にもともと台帳ID(例 `ZZ-001：`)が書かれている場合は、そのまま残し、サイドカーの `ledger_ids` と一致させます。

## 3 数字の印
対象は、算用数字(全角を含む)を含む表記です。漢数字だけの数量(三千人など)は対象外で、印を付けずに `annotation_notes` に記録します。台帳IDの形(`ZZ-001`、`QQ-AB-006` のような英字-数字)は数字として扱わず、印を付けません。

### 3-1 表記(surface)の取り方
- 数字・単位・ヘッジ語を**1つの表記**として、印は表記の末尾に付けます。例: `約3.4％【中核数値】`、`1リットル180円【中核数値】`、`2,300件超【中核数値】`。
- ヘッジ語は表記に含めます。前に付く語: 約・およそ・ほぼ・最大・最大で・少なくとも・数。後ろに付く語: 超・以上・以下・未満・前後・近く。数字に直接つかない語(「一時」「当面」、「を上回って」)は含めません。
- 範囲(`3〜5％`)は1つの表記(kind=range)。日付と時刻が続くもの(`5月8日午前9時30分`)は1つの表記。「翌14日」は数字の部分 `14日` を表記にします。
- 同じ表記は記事の中のどこでも同じ分類(同じ印)にします。短い表記が長い表記の一部になるとき(`2031年9月` が `2031年9月20日` の中に入るとき)は、その場所では長い方に1回だけ印を付けます。

### 3-2 種類(kind)
- `magnitude`: 割合・金額・件数・個数・価格・倍率・順位などの量。
- `date_time`: 年月日・年月・時刻・期間(月が含まれるもの)。
- `range`: 範囲。
- `year`: 年だけ(`2031年`)。常に周辺です。
- `ordinal`: 識別子としての序数(`第9条`、`第12回会合`)。常に周辺です。
- `name_embedded`: 名称の一部の番号(`Hyperion 12`、`Spring 2031`)。常に周辺です。
番号を変えると別のものを指す表記は識別子(ordinal か name_embedded)で、数量ではありません。番号を変えると量や日付が変わる表記は数量です。量か名称内番号か迷ったら、名称内番号を選びます。

### 3-3 概念(concept)
同じ台帳データを指す表記を1つの「概念」にまとめ、サイドカーの `concept` に同じ名前を書きます(例 `2031年9月20日` と `2031年9月` は同じ概念)。次の場合は必ず同じ概念にします: 台帳IDが共通で短い表記が長い表記に含まれる、台帳IDが共通で主数字(3-5)が同じ。同じ概念の中で、`kind` はそろえます。別の概念の表記同士は、この条件に当てはまりません。

### 3-4 台帳ID
その数字が載っている台帳の事実IDを `ledger_ids` に全て書きます(複数可)。台帳にその数字がない場合は空の配列にし、中核にはできません(周辺にして、`unmapped_claims` に type=`new_number` で記録します)。数字の表記は、ニュース欄の表記のままにします(台帳の表記に直しません)。

### 3-5 中核と周辺の決め方(次の手順を機械的に実行)
1. 主数字: 表記の末尾の数字の並びを「主数字」とします(範囲は両端の2つ)。例 `1リットル180円`→180、`約3.4％`→3.4、`3〜5％`→3と5、`2,300件超`→2300。数字は10進数として比べます(`4.00`=`4`=`04`、`1,500`=`1500`)。
2. 適格かどうか(概念の表記のどれか1つが適格なら、その概念が適格):
   - 量(magnitude / range)は、主数字が、紐付く台帳の事実の `numeric_value` 欄の数字に含まれていれば適格です。`(numeric_scope: …)` の中の数字は除いて比べます。台帳に `numeric_value` 欄が1件もない場合に限り、`statement` の中の数字で代わりに比べます。
   - 日付(date_time)は、表記に月があり、台帳の事実の `date_or_period` 欄の**先頭の日付表現**(和文の `2031年9月20日` も、`2031-05-08 09:30 EDT` のような形も)と、表記にある年・月・日(・時刻)が全て一致すれば適格です。表記に無い要素は問いません。年だけ・日だけの表記は不適格です。台帳に `date_or_period` 欄が1件もない場合に限り、`statement` の最初の日付表現で代わりに比べます。Storylineに出るかどうかは条件にしません。
   - year / ordinal / name_embedded は常に不適格です。
3. 数える概念の数 n は、種類が magnitude / date_time / range の概念の総数です。上限は `max(3, min(6, floor(n/2)))` です(n≦7 なら3、n=8〜9 なら4、n=10〜11 なら5、n≧12 なら6)。nが小さいと、適格な概念が全て中核になることもあります(上限は式で決まります)。
4. 適格な概念を次の優先順に並べます: (1)Storylineに出る量(magnitude / range)、(2)それ以外の量、(3)日付。同じ順位の中では、ニュース欄の上から先に出てくる順です。
5. 先頭から上限の数までが中核(`【中核数値】`)、残りの適格な概念と不適格な概念は全て周辺(`【周辺数値】`)です。同じ概念の表記は全て同じ印にします。
6. 上限のために周辺になった適格な概念は、`annotation_notes` に「cap超過で周辺化」と記録します。

## 4 台帳に無い記述
- ニュース欄に書かれているが台帳に無い記述には、印を付けません。サイドカーの `unmapped_claims` に `{"text": "…", "type": "…"}` で記録します。type は次のどれか: `new_fact`(新事実)、`new_number`(新数値)、`new_causal`(新因果)、`generalization`(一般化)、`specification`(具体化)、`qualifier`(限定)。これだけでは作業を止めません。
- 次の2つのときだけは、注記をやめて「STOP」を返します: (i)Storyline(記事の骨格)の主張そのものが台帳に無い。(ii)台帳に無い数字が、中核になりうる量または日付の形でStorylineにある。
- 台帳に書かれていない知識で、事実の根拠や数字の正しさを補ってはいけません。

## 5 迷ったときの既定
迷ったら、必ず `annotation_notes` に `{"where": …, "question": …, "options": […], "chosen": …, "rule": "§番号"}` を記録し、次の既定に従います。
1. 分けるか迷う → 分けない。
2. 中核か周辺か迷う → 周辺(適格であることを台帳で確認できない限り周辺)。
3. 量か名称内番号か迷う → 名称内番号。
4. 紐付く台帳の事実が複数で決められない → 該当するIDを全て `ledger_ids` に書く。
5. ヘッジ語を含めるか迷う → 数字に直接ついていれば含める。
6. 規則に当てはまらない状況 → 記録して、印を付けない側にする。

次の形式で、そのまま返します(前後に説明文を付けません)。

```
=== ANNOTATED_BRIEF_END ===
=== SIDECAR_JSON_BEGIN ===
(サイドカーJSON)
=== SIDECAR_JSON_END ===
```

## 7 出す前の自己点検
- 注記版から3種類の印と定義済みの改行の挿入を取り除くと、元のニュース欄と一字一句同じになるか。
- 【事実N】は上から1,2,3…の連番で、箇条書きの行頭(`- ` の直後)にだけあり、複合の印がないか。
- 本文の算用数字が、全て `numbers` のどれかの表記に含まれているか(台帳IDの形を除く)。
- `numbers` の `class` が、3-5の手順の結果と一致しているか(適格で上限の内側なのに周辺にしていないか、不適格なのに中核にしていないか)。
- 同じ表記が全ての場所で同じ印か。同じ概念の `kind` がそろっているか。
- `spec_sha256`・`brief_sha256`・`annotator` を依頼文の値のとおりに写したか。
