## 1. 目的と役割境界

**目的**: Fact Lock + Astraで生成した記事について、開発時に人間が『真の重大NG』を見つけやすくする支援機構(開発用Risk Flagger)を設計・検証する。量産Production用Checkerではない。品質保証の主軸は上流のFact Lock + Astra設計に置き、本機構は『人間の見逃しを減らす補助』に限る。

**しないこと(4つ)**:
1. 合否判定をしない(PASS/FAILを出さない)。
2. Productionを止めない(STOP・Gateに接続しない)。
3. Rewriteしない。
4. 自動修正しない(修正案の本文反映もしない)。

**役割は1つ**: 『この箇所は人間が確認した方がよい』とFlagを立てる。100%検出は求めない(完全性を追って開発が終わらなくなることを避ける)。ただし『真の重大NGは拾う』『真の重大でないものは拾わない』を目指す。軽微は今回のターゲット外で、重大/非重大の2値のみを扱う。

**非目標**: 万能Checkerの再構築、Production Checkerの置換・廃止の判断(『廃止候補』のままで正式判断は別)、Production配線。

## 2. 入力と出力

### 入力
- 台帳: `verified_fact_ledger.txt`(Fact ID・逐語・scope・conditions・notes_for_writer 付き)。
- 記事: JA最終稿(`ja_writer/revision2.md`)と EN(`b1b/article.md`、`a2/article.md`)。文単位に分割し、段落・見出し位置を保持する。
- 与えない物: 既存Checkerの判定・Rewrite履歴・人間ラベル・他検出器の出力(盲検。先行Trial `WRITER-EVAL-DUAL-LLM-METHOD-TRIAL-01` と同方針)。

### 出力(Flag 1件)
| フィールド | 内容 |
|---|---|
| flag_id | 記事ID+連番 |
| span | 対象文(逐語)・記事内の行/文番号 |
| accident_type | rollback方向反転 / 主体対象入替 / 否定反転 / 数量時系列 / 不在断定 / その他(6区分。ケースバンクと同一) |
| evidence | 根拠Fact ID(複数可)と台帳逐語(該当部分のみ)。『台帳に無い』型は『該当Factなし』と明記 |
| confidence | high / medium / low の3段(確率ではない。校正は保留セットの結果で事後に検証) |
| review_question | 人間向けの確認質問(日本語、1〜2文、はい/いいえで答えられる形)。例:『台帳は「ロールバック」(取り下げ)と書いていますが、この文は元に戻した(復元した)と読めます。この読みで問題ありませんか』 |
| source_detector | どの検出器が立てたか(複数可) |

出力は記事ごとに優先順(confidence→タイプ→記事内順)で並べ、1記事あたりの確認量を見積もれる形にする。同一箇所に複数検出器のFlagが立った場合は統合し、`source_detector` を併記する(統合後の件数を『Flag数』とする)。

## 4. 評価KPIと判定線(事前登録)

用語: 『ヒット』= 重大ケースの対象文(または同一Factの同一段落内で、その文を含む連続2文以内)にFlagが立つこと。種別一致(`accident_type`)は別途記録するが、ヒット成立の条件にはしない。『誤Flag』= 非重大ケース(ラベル根拠区分を問わず)の対象文に立つFlag。

| KPI | 定義式 | 事前登録の判定線(保留セット、検出器構成を確定した後の1回の評価) |
|---|---|---|
| **KPI1 既知重大Recall** | `Recall_all = ヒットした重大ケース数 / 重大ケース数`(保留11件)。`Recall_human = ヒット数 / 人間確認済み重大数`(保留3件=K01・K02・K11。K03は開発側のため含めない) | 合格 Recall_all ≥ 70%(11件中8件以上)かつ Recall_human ≥ 2/3。**不合格線**: Recall_all < 50%。95%区間(Wilson)を必ず併記(n=11で1件=約9ポイント)。100%は求めない |
| **KPI2 Flag精度** | (a) `FPR_clear = 誤Flagした『非境界』非重大ケース数 / 非境界非重大ケース数`(ユーザー確認A、台帳逐語に近い機械抽出、Sonnet『問題なし』)。(b) `FPR_boundary`(境界・軽微の非重大に立った割合)は参考値として別掲(境界はFlagされても誤りとは限らない)。(c) `Precision_cb = TP Flag数 / (TP Flag数 + 誤Flag数)`(保留セット。重大の割合30%程度のため実運用の精度を過大評価する旨を併記)。(d) 記事単位では§KPI5の人間裁定による精度 | 合格 FPR_clear ≤ 20% かつ Precision_cb ≥ 50%。不合格線 FPR_clear > 35% |
| **KPI3 人間確認量** | `Flags/記事 = 全Flag数 / 記事数`(新腕・旧腕で記事の存在する言語版ごと、JAとENを別集計)。確認所要は1 Flagあたり30秒(台帳照合込み)と仮置きして `分/記事` を算出 | 合格 平均 ≤ 5 Flag/記事/言語版(約2.5分)。不合格線 > 12 Flag/記事/言語版。分布(最大値・中央値)も併記 |
| **KPI4 既知事故への強さ** | 過去事故6系統(Rollback方向反転=K01/K03、開示対象の取り違え=meta-p2r2-02、『初めて』の範囲拡張=sw-p2r2-02、20%の対象入替=hormuz-T0M0r2-01、時期の創作=RC-K16、因果・仕組みの創作=Safety-B3/B4-a/RC-K20等)ごとに、開発+保留で再現できた系統数/6。Rollbackは別に、実ケースK01・K03(2/2)+合成S-12・S-13(2/2)+忠実文K12に誤Flagなし | 合格 Rollbackは4/4かつK12誤Flagなし、かつ6系統中 ≥ 4系統再現。不合格線 Rollbackで実ケース1件でも未検出が保留で再現(=主目的の失敗) |
| **KPI5 未知ケース有用性** | 新腕・旧腕の実記事に立ったFlagのうち、既知ケース(ケースバンク)と無関係な箇所から最大20件を層別無作為抽出し、**人間(ユーザー)が裁定**: 重大/要確認で価値あり=有用、問題なし=無用。`Useful_rate = 有用Flag数 / 裁定Flag数`。加えて『新規に発見された重大候補数』を記録 | 合格 Useful_rate ≥ 40% または 新規重大候補≥1件かつ Useful_rate ≥ 25%。不合格線 Useful_rate < 15%。**裁定はユーザーが行う**。ユーザー不在時のFable/Sonnet仮裁定は『暫定』と明記し、暫定のままではVALIDATED確定に使わない(USER_DECISION_REQUIRED扱い) |

補助指標: 種別一致率、確信度別のヒット率(校正)、検出器別の単独寄与(§5)、1 Flag当たり費用、再現性(同一入力3 repでFlag集合の一致率。LLM検出器のみ)。

**サンプルサイズの限界**: 保留の重大11件(人間確認済み3件)で統計的な確定はできない。結論は『この方式で人間レビューが実用上助かるか』の定性的判断と、区間つきの数値を併記する形にする。

### 判定の閉じ方(Closeout分類の事前規則)
- VALIDATED(開発用Risk Flagger方式): KPI1〜4が合格かつKPI5が合格(人間裁定済み)。Production採用ではない。
- REJECTED: KPI1またはKPI2またはKPI4のいずれかが不合格線を割り、改善ループ3回後も回復しない場合。
- USER_DECISION_REQUIRED: KPI1〜4は合格だがKPI5が暫定止まり、または拮抗する複数構成でFable判断が事業判断になる場合、またはSTOP条件(§10)に該当した場合。

## 5. 検出器構成の比較計画

委任_01Bが `er052_output/writer_dev_risk_flagger_01/detectors/` に作成する検出器候補・harness骨格を参照する(**本書は01Bの内容を複製・確定しない。01Bのファイルは01Aでは未参照・未変更**)。比較する構成の枠組みだけをここで固定する。

| 構成 | 内容 | 想定コスト | 狙い |
|---|---|---|---|
| **C0 決定論のみ** | ルール・語彙対・正規表現。Rollback/復元語彙対、数値・日付のFactとの突合、否定語/不在断定語(『ない』『not』『no one』『確認されていない』等)の検出、台帳にない固有名・数値の検出。API¥0 | ¥0 | 既知事故の再現と、高速な前段フィルタ |
| **C1 事故タイプ別専用Detector(LLM)** | Rollback方向反転専用/主体・対象入替専用/否定反転専用/数量・時系列専用/不在断定専用。各々短い専用Prompt+台帳の該当Factのみ+対象文。Sol | 小(短文) | 事故タイプに特化し誤Flagを減らす。タイプ別の寄与を測る |
| **C2 万能Flagger(LLM、1本)** | 1つのPromptで全タイプを探す。Sol | 中 | 万能vs専用の比較基準。未知タイプへの汎用性 |
| **C3 組合せ** | C0(決定論)で候補抽出→C1専用Detectorで確認、またはC0∪C1∪C2のunion後に重複統合 | 中 | 再現率と精度の両立 |
| **C4 確認層** | C3で出たFlagのみを最上位モデル(Astra)で再確認し、確信度を調整(Flagを消さず『低』に下げるのみ。人間に見せる件数は§KPI3で管理) | 小(Flag数に比例) | 誤Flagの削減。**Flagを自動的に削除しない**(見逃し防止) |

比較手順(小さく切って絞る):
1. **要素Trial(開発セット+合成参考)**: C0、C1の各専用、C2をそれぞれ単独で開発セットに適用し、KPI1〜3相当(開発側)とタイプ別ヒットを測る。1構成1repから開始し、有望なものだけ3repで再現性を測る。
2. **組合せ**: 要素Trialの結果を見てC3の組合せを最大2案に絞る。
3. **確認層**: 最有望1案にC4を載せた場合の誤Flag削減と見逃し(Flagを下げたことで人間が見落とすリスク)を測る。
4. **記事単位**: 最終候補1〜2案を新腕・旧腕の記事(JA/EN)に適用し、KPI3・KPI5用のFlagを得る。
5. **保留セット最終評価**: 確定した1構成を1回だけ適用してKPI1・2・4を確定する。

『万能 vs 事故タイプ別専用』の判定材料は、(1) 開発セットでのタイプ別Recall、(2) 同じ費用での誤Flag率、(3) 保留セットでの未知タイプ(タイプ『その他』)への反応、の3つで比較する。

## 9. 改善ループ(最大3回)

Opusレビューを含めて最大3回。ループ1回=『結果を見て検出器・Promptを変更し、開発セットで再測定する』1サイクル。
1. ループ1: 要素Trialの結果を見た構成の絞り込み・Prompt修正(開発セットのみ)。

保留セットの最終評価はループに数えず1回のみ。保留の結果を見たあとの調整はしない(した場合は『保留汚染』として結果を参考値扱いにする)。ループ上限到達で目標未達なら、REJECTED/USER_DECISION_REQUIREDとして閉じる。

## 11. 想定リスク・限界(事前に認識している点)

1. ラベルの弱さ: 重大17件のうち人間確認済みは4件で、10件がSonnet判定、3件がFable確定。ラベルの誤りがRecall・精度をゆがめる。→ 人間確認済みだけのRecallを必ず併記する。
2. 先行Trialの教訓: Luna/Sol/DeepSeekのいずれも既知重大を安定検出できなかった。万能LLMへの過信を避け、決定論(C0)とタイプ別専用(C1)を主軸に比較する。LLMの確信度は信用せず、再現性(3rep一致)で見る。
3. Rollbackは同型の過学習リスク: K01/K03が同一Factで、かつ過去事故の本命のため、開発側にK03、保留側にK01を置いたが独立性は弱い。→ 合成S-12・S-13と、別Fact・別表現のRollback類似文(今後の人間確認で追加できれば)で補う。
4. 新腕に重大ラベルが0件: KPI5は人間裁定に依存する。裁定コスト(ユーザー作業)が最大20件で収まる設計にした。
5. 『否定反転』の実記事サンプルが0件: タイプ別能力は合成参考セット(14件)でしか測れず、実記事での有効性は未検証になる。
6. 数百件規模の統計ではない: 結論は区間つきの参考値。VALIDATEDでも『開発用の補助として使ってよい』にとどまり、Production採用や、Production Checker廃止の根拠にはならない。
