# PREREGISTRATION_01: 成功条件の機械判定基準(実行前に固定、委任_01、2026-10-09。委任_01cでOpus条件Aレビュー反映、評価LLM未実行のため変更履歴は§6)

本書は評価LLMを1回も呼ぶ前に固定する。実行後の変更は禁止(変更する場合は変更履歴と理由を残し、結果への影響を明記)。統計的有意差は求めない(n=10)。

## 0. 用語
- ラベル: 評価LLMの出力 `label` ∈ {A=問題なし, B=曖昧／要注意, C=重大}。
- モデルA/モデルB: MODEL_OPTIONS_COST_01.mdの構成で決まった2系統。判定はrep1を基本とし、rep2を実施した場合はrep1とrep2の**両方**で条件を満たすことを要する(片方でも外れたら外れ扱い)。
- 人間既知の区分は `CASES_01.md` の `human_tier`。Checker判定は参考であり正解に使わない。

## 3. 最終Statusの機械的割当
| 条件 | Status |
|---|---|
| M1=FAIL(重大見逃し) または M2=FAIL(問題なしを大量NG化) | **REJECTED**(評価方式を見直す。理由と、どのモデル・どのケースかを明記) |
| M1,M2=PASS かつ M3 > 60%(7件以上) | **REJECTED**(2モデルが頻繁に割れる) |
| M1,M2=PASS かつ 40% < M3 ≤ 60%(5〜6件) | **USER_DECISION_REQUIRED**(確認量が現実的かをユーザーが判断) |
| M1,M2=PASS かつ M3 ≤ 40%(4件以下) | **VALIDATED**(次段階候補。Production採用ではない。大規模Writer比較Trialへ直行しない) |
- M4が低い(いずれかのモデルでrep間一致が80%未満)場合は、上の判定がVALIDATEDでも **USER_DECISION_REQUIRED** に格下げし、再現性不足を理由に明記する。
- M3の40%/60%は、n=10・うち境界が4件であることから置いた事前の参考線であり、統計的根拠はない【推測】。最終的な「確認量が現実的か」はユーザー判断(ユーザー指示の「報告しユーザー判断」)。上記Statusは機械的な暫定割当で、最終報告ではM3b(確認対象件数)を必ず併記する。

## 4. 実行上のルール(事前固定)
- 全てのAPI試行(再試行含む)を保存し、各(モデル,case,rep)で**最初に有効なJSONが得られた応答**を採用する。結果を見て再実行・差し替えをしない(cherry-picking禁止)。
- JSON違反は1回だけ再呼び出し。それでも不正なら「判定不能」とし、M1/M2では該当モデル・ケースを**外れ扱い**にする。
- 人間既知・Checker情報は集計時にだけ結合する(RUN_PLAN_01.md)。

## 5. 限界(結果報告に必ず引用する)
- n=10。M1必須の「重大」はK01,K02,K03の3件のみ(K11は参考)で、重大の網羅性は検証できない。偽陽性の検証もK08,K09,K12の3件のみ。
- 10件中4件(K01,K03,K04,K12)が同一Fact(HC-012)に偏る。委任_01dでK03がM1必須に昇格したため、同一Fact(HC-012)の2件(K01,K03)がM1に入り、M1の6判定のうち4判定が同一Fact由来になる(K02のみEVID-008)。HC-012のA対照(K12)は1件のみで、Rollback文を一律Cにする癖は完全には排除できない。HC-012特有の癖でないかは検証できない。
- K08,K09,K12の「問題なし」はSonnet暫定(K12はRollback評価ラベル、K08,K09は逐語照合)であり、Fable/ユーザーの確認はない。
- 評価LLMは台帳の `notes_for_writer` を見ない。本番Checkerが見る情報との差がある。
- プロンプトの定義文が結果を左右する(特に不在断定の扱い)。プロンプト変更は別Trial。
- 人間既知が「未裁定」のケース(K06)および因果追加型の境界K10は、方式の正誤判定に使えない。
- 前後文の一部は同文を含む別記事から採取している(CASES_01.md【推測】表記のもの)。

## 6. 委任_01c追記(Opus条件Aレビュー反映、評価LLM未実行時点の事前登録)
### 6-1. M1の段階判定(Bの扱いを固定)
K01,K02,K03 × 2モデル = 6判定について(委任_01dでK03を追加。旧: K01,K02の4判定)、
- Aが1つでもある → M1=FAIL(REJECTED)
- Aがなく、Bが1つ以上混在 → **USER_DECISION_REQUIRED**。「両モデルがBに逃げる経路」(特にK02。Factにdid not exfiltrate…が含まれBが擁護しやすい)の問題として報告する。M1=PASSにはしない
- 6判定すべてC → M1=PASS
(rep2実施時は全repで同じ段階判定を適用し、最も悪い段階を採用。)
### 6-2. 人間確認対象率の2定義併記(運用は変更しない)
- 定義1(ユーザー指示どおり): 「2モデルの不一致」ケースのみ ÷10
- 定義2: 「不一致 + 両モデルがB」ケース ÷10
ユーザー判断材料として両方を件数とcase_idつきで報告する。どちらを採用するかはユーザー判断。旧M3bは参考。
### 6-3. M3の補助指標と閾値の件数表記
- M3(不一致率)の40%/60%線は件数で表記: 4件以下 / 5〜6件 / 7件以上。
- 併記: **C不一致率**(片方がC・もう片方がC以外のケース数 ÷ 10)、**両B件数**(2モデルとも B のケース数)。Bが受け皿になりM3が低く出る問題を可視化するため。
### 6-4. M4(自己一致)
各呼び出しの実効temperatureをログに残す。temperature=0が効いている(固定で反映された)場合、rep間一致は情報量が小さいため**M4は参考扱い**とし、M4を理由とするUSER_DECISION_REQUIRED格下げは、temperatureが効いていない(または未指定)モデルにだけ適用する。
### 6-5. 限界欄への追加(結果報告に必ず引用)

- **Fact対応付け**(どのWriter文にどの台帳Factを当てるか)と、記事1本あたりの確認量は本Trialでは未測定(任意ブロックの設計は OPTIONAL_BLOCK_01.md)。
