# PREREGISTRATION_01: 成功条件の機械判定基準(実行前に固定、委任_01、2026-10-09)

本書は評価LLMを1回も呼ぶ前に固定する。実行後の変更は禁止(変更する場合は変更履歴と理由を残し、結果への影響を明記)。統計的有意差は求めない(n=10)。

## 0. 用語
- ラベル: 評価LLMの出力 `label` ∈ {A=問題なし, B=曖昧／要注意, C=重大}。
- モデルA/モデルB: MODEL_OPTIONS_COST_01.mdの構成で決まった2系統。判定はrep1を基本とし、rep2を実施した場合はrep1とrep2の**両方**で条件を満たすことを要する(片方でも外れたら外れ扱い)。
- 人間既知の区分は `CASES_01.md` の `human_tier`。Checker判定は参考であり正解に使わない。

## 1. 必須条件(M1〜M2)
| ID | 内容 | 機械判定 |
|---|---|---|
| M1 重大の捕捉 | 人間確認済み・Fable確定の重大 K01(meta restored)とK02(jb9k不在断定)を、2モデルとも C にする | K01,K02 × 2モデル = 4判定がすべて C。1つでもA/BならM1=FAIL |
| M2 過剰NG | 明らかな問題なしK08,K09,K10に対するB/C付与が少ない | 3ケース×2モデル=6判定のうち、B/Cが付いた判定が1以下。かつC判定は0。2以上、またはCが1つでもあればM2=FAIL |
- K03(A5-0 gold)はユーザー個別確認ではなくFable確定のため、M1の必須には含めず、参考として「2モデルともCか」を報告する。
- K01はユーザー個別ラベルではなく「Fable確定+ユーザーが重大見逃しと呼称」の区分(CASES_01.md)であることを結果報告に明記する。

## 2. 報告指標(合否には使うが、閾値は参考線)
| ID | 内容 | 算出 |
|---|---|---|
| M3 不一致率 | 2モデルのラベルが異なる件数÷10 | rep1で算出(rep2実施時はrepごとに算出し併記) |
| M3b 人間確認対象率 | 少なくとも1モデルがC、または2モデルが不一致のケース数÷10 | 「現実的な確認量」の指標。ユーザー判断用に件数と該当case_idを提示 |
| M4 自己一致 | 同一モデルのrep1とrep2でラベルが一致する割合 | rep2実施時のみ。2モデル別に報告 |
| M5 境界例の分布 | K04〜K07の各モデルラベル、2モデルの一致/不一致、人間既知(未裁定含む)との並置 | 合否に使わない。人間既知が未裁定のケースは「一致/不一致」だけを報告し正誤を判定しない |
| M6 Checker参考比較 | 各ケースでChecker参考判定(見逃し/検知)と評価LLMラベルを並置 | Checkerを正解にしない。K01,K02で「Checkerは見逃し・評価LLMはC」となるかを事実として記載 |

## 3. 最終Statusの機械的割当
| 条件 | Status |
|---|---|
| M1=FAIL(重大見逃し) または M2=FAIL(問題なしを大量NG化) | **REJECTED**(評価方式を見直す。理由と、どのモデル・どのケースかを明記) |
| M1,M2=PASS かつ M3 > 60% | **REJECTED**(2モデルが頻繁に割れる) |
| M1,M2=PASS かつ 40% < M3 ≤ 60% | **USER_DECISION_REQUIRED**(確認量が現実的かをユーザーが判断) |
| M1,M2=PASS かつ M3 ≤ 40% | **VALIDATED**(次段階候補。Production採用ではない。大規模Writer比較Trialへ直行しない) |
- M4が低い(いずれかのモデルでrep間一致が80%未満)場合は、上の判定がVALIDATEDでも **USER_DECISION_REQUIRED** に格下げし、再現性不足を理由に明記する。
- M3の40%/60%は、n=10・うち境界が4件であることから置いた事前の参考線であり、統計的根拠はない【推測】。最終的な「確認量が現実的か」はユーザー判断(ユーザー指示の「報告しユーザー判断」)。上記Statusは機械的な暫定割当で、最終報告ではM3b(確認対象件数)を必ず併記する。

## 4. 実行上のルール(事前固定)
- 全てのAPI試行(再試行含む)を保存し、各(モデル,case,rep)で**最初に有効なJSONが得られた応答**を採用する。結果を見て再実行・差し替えをしない(cherry-picking禁止)。
- JSON違反は1回だけ再呼び出し。それでも不正なら「判定不能」とし、M1/M2では該当モデル・ケースを**外れ扱い**にする。
- 人間既知・Checker情報は集計時にだけ結合する(RUN_PLAN_01.md)。

## 5. 限界(結果報告に必ず引用する)
- n=10。K01,K02以外の「重大」は3件目(K03)が参考のみで、重大の網羅性は検証できない。偽陽性の検証もK08〜K10の3件のみ。
- 10件中5件が同一Fact(HC-012)に偏る。HC-012特有の癖でないかは検証できない。
- K08〜K10の「明らかに問題なし」はSonnet暫定+本委任での逐語照合であり、Fable/ユーザーの確認はない。
- 評価LLMは台帳の `notes_for_writer` を見ない。本番Checkerが見る情報との差がある。
- プロンプトの定義文が結果を左右する(特に不在断定の扱い)。プロンプト変更は別Trial。
- 人間既知が「未裁定」のケース(K06,K07)は、方式の正誤判定に使えない。
- 前後文の一部は同文を含む別記事から採取している(CASES_01.md【推測】表記のもの)。
